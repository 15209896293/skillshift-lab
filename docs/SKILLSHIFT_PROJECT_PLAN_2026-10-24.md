# SkillShift 项目总体计划书

**编制日期：** 2026年10月24日  
**项目阶段：** R0/R0.5 研究准备与合成产品原型阶段  
**计划性质：** 全项目总体说明与阶段推进依据

## 项目摘要

SkillShift 研究 Agent 参与职业数字任务后，学习者的基础能力、人与 Agent 的协作过程和能力迁移之间有什么关系。项目关心的不是“学生有没有用 AI”，而是学生能否理解任务、判断建议、验证结果、纠正问题，并在条件变化时继续完成工作。

SkillShift Lab 是研究与方法体系；SkillShift Studio 是组织教学任务、支持学生实践、呈现必要过程证据并供教师复核的产品化载体。Studio 的价值在于让允许 AI 协同的任务更容易布置、完成、解释和反馈，不在于与通用 Agent 比拼模型能力。

项目当前处于研究准备和合成原型阶段。近期以 Python + CSV 数据处理任务作为首个产品与任务设计入口，先完成可审查的任务、证据和教师—学生工作闭环，再根据专家意见和客观证据决定是否开展小范围验证或扩展。当前样例不等于正式 Benchmark；已有原型、测试和历史运行记录也不等于真实课堂、学习效果、生产系统或安全执行能力。

## 一 项目要解决的问题

Agent 可以参与编程、数据处理和故障诊断等工作，但任务产物完成，不代表学习者理解了过程或能在新情境中独立判断。只看最终答案，教师难以知道学生是否检查过结果、发现过错误、承担过关键决定；只记录大量操作，也不能据此直接判断能力、努力或是否作弊。

项目要回答一个实际问题：在职业任务中允许 Agent 协作时，如何保留学习者应承担的判断与验证责任，让教师能依据少量、可解释的任务证据提供反馈；进一步研究这些协作表现与后续迁移任务之间是否存在稳定关系。

项目不预设 Agent 一定提升学习效果，也允许研究结果不支持预期。任务无效、证据无法解释或教师复核成本过高，都应成为调整或停止的依据。

## 二 项目定位与组成

### 2.1 SkillShift Lab

Lab 是项目的研究主体，围绕职业任务和人机分工开展问题定义、任务设计、证据分析及方法检验。研究对象不是某个模型的排行榜，而是 Agent 参与后职业任务中的知识要求、基础能力、协作责任、评价方式和迁移表现如何变化。

### 2.2 SkillShift Studio

Studio 是 Lab 的教学工作平台和研究基础设施。其目标闭环为：

```text
教师定义任务、允许的 AI 协作方式和交付要求
→ 学生在任务上下文中使用 Agent 并承担验证、说明或补正责任
→ 平台整理任务产物和必要的过程事实
→ 教师复核并给出反馈或补正要求
→ 学生回应并提交修订结果
```

Studio 面向教师和学生分别提供任务组织、实践、提交与复核入口。教师保留教学判断权；系统不自动给学生定成绩、贴能力标签或判定作弊。产品运行数据不会自动成为研究数据。

### 2.3 研究关系

项目以职业任务为连接点：研究提出需要观察的问题，Studio 提供任务和复核流程，任务产生结果与必要过程证据，研究在取得授权并满足治理要求后分析这些材料，结论再用于改进任务和教学设计。工具运行本身不是研究结论。

## 三 研究框架与问题

项目采用 Foundation—Process—Transfer 作为基本研究结构，并将任务结果 Outcome 作为辅助证据单独解释：

在教学衔接上，Foundation Track（基础能力轨）指向学习者已有的基础知识和独立操作；Agent Track（人机协作轨）指向在更复杂职业任务中使用 Agent、同时承担委托、判断、验证和接管责任。项目研究两者如何连接以及是否发生迁移，不要求学校立即改变正式课程、考试或培养方案。教师、导师、社团或训练营的非计分练习可以作为未来走查入口，但真实参与仍须单独获得授权。

| 部分 | 关注内容 | 不能单独证明什么 |
| --- | --- | --- |
| Foundation 基础能力 | 学习者在无 Agent 或有限 Agent 帮助时，能理解和完成什么 | 不能代表全部职业能力 |
| Process 协作过程 | 学习者如何分解任务、判断建议、验证结果、纠错、接管和说明 | 过程事件本身不能证明理解或能力 |
| Outcome 任务结果 | 交付是否符合任务要求、发生哪些错误、完成条件是否满足 | 产物正确不能证明学习已经发生 |
| Transfer 能力迁移 | 条件改变、帮助减少或任务变体后，学习者能否重新组织能力 | 一次后测不能代表稳定职业胜任力 |

Agent Capability 用于说明和校准任务中的 Agent 条件，不作为项目唯一成果。项目的核心研究问题是：

> 在任务版本与 Agent 条件明确的情况下，学习者在协作中的理解、验证、纠错与接管表现，是否能够帮助解释其在变化条件下的迁移任务表现？教师能否以可接受的工作量，依据任务相关证据开展复核和反馈？

这是一组待检验问题，不是已得到答案的结论。正式研究设计还须明确比较条件、样本来源、测量方法、分析计划和可能推翻假设的结果。

长期研究还可涉及职业任务变化、Agent 能力边界、评价任务的适用性和教学调整。个人技能记录（Personal Skill Memory）或成长记忆只有在其用途、数据治理和有效性得到单独论证后再考虑，不属于当前 Studio 的自动能力画像功能。

## 四 首个任务与产品范围

### 4.1 首个任务入口

第一条产品与研究设计路径采用 Python + CSV 数据处理/一致性检查任务。它用于验证任务定义、学生责任、结果检查和教师复核流程，不限制项目未来的任务范围。SQL/数据库诊断及其他任务域暂不并行扩张。

已有 Python + CSV 样例和确定性验证材料属于合成候选资产。它们尚不等同于经教师或行业人员确认的正式任务族、冻结 Benchmark 或可用于学生评分的规则。正式冻结前需核实职业来源、任务目标、参考结果、正反例、验证规则及迁移变体。

### 4.2 R0 产品切片

R0 先验证教师低负担和学生有效参与两个产品事实：

1. 教师能否用有限步骤发布任务、看到有理由的待复核内容，并完成反馈或补正处理。
2. 学生能否在允许 Agent 协作时完成任务要求的验证、解释、纠错或接管，而不只是转交 Agent 输出。

学生项目工作空间是已确认的产品切片方向，但不是“任意访问学生电脑的通用 Agent”。任务上下文、项目材料和 Agent 建议可逐步纳入目标体验；在相应安全 Gate 关闭前，不运行真实学生或外来代码、不安装依赖、不开放任意 Shell 或网络工具。确定性 Agent 适配器只可验证流程编排，不能称为真实模型能力。

首期不建设完整 LMS、成绩管理、自动能力画像、外部 AI 检测、全桌面监控或与主流 Agent 竞争的通用平台。多任务域、Personal Node、Managed Sandbox、真实模型、身份、持久化、生产数据库和部署均须单独评估和授权。

## 五 任务与证据设计

每个任务在进入验证前，应说清楚以下内容：

1. 任务对应的职业或教学问题、交付物和质量要求。
2. 使用的任务材料、环境、版本及允许的 Agent 协作方式。
3. 学生必须承担的验证、解释、纠错、接管或补正责任。
4. 结果如何检查，检查规则由谁确认，哪些失败属于环境问题。
5. 教师可以看到哪些任务相关事实，并可采取哪些反馈动作。
6. 若未来用于研究，另行说明目的、授权、最小采集、去标识化、保留和退出方式。

证据分为任务结果、过程事实、教师动作和研究数据。提交包只应包含教师复核所需的产物、验证结果、必要说明和事件引用；不以保存全量日志为目标。平台内未观察到的外部活动不可推断。粘贴、错误、少量编辑、相似度或过程缺失不能单独证明作弊、能力不足或努力程度。

确定性验证器可以检查明确的任务规则，但不能代替领域审查，也不能自动转化为学生成绩。任何能力或学习结论都需要与问题匹配的研究设计和证据支持。

任务设计可用任务图（Task Graph）描述步骤、依赖和交付，用证据契约（Evidence Contract）说明每一步需要什么可复核材料、由谁负责。独立任务检查器只核对明确的结果规则；其输出和适用条件应可追溯、可解释。此类结构用于把任务和证据说清楚，不意味着当前已实现完整任务引擎、隐藏评分系统或自动评价产品。

## 六 项目实施阶段

本计划按阶段门推进，不预设未经确认的日期、经费、参与者数量或结果。

| 阶段 | 工作重点 | 主要产物 | 通过条件 |
| --- | --- | --- | --- |
| B0 项目基线 | 盘点并保全代码、计划、规格、测试和运行证据；区分当前源码与历史记录 | 可审计状态快照、资产地图、复现检查清单 | 文件状态、日期、验证范围及未决事项可追溯 |
| R1 任务与研究设计 | 审查 Python + CSV 任务来源，确定版本、参考解、正反例、验证规则和迁移变体；写明研究比较与分析计划 | 可供教师/领域人员审阅的任务包与研究方案 | 审阅者能判断任务是否有效、如何判定、什么结果会推翻假设 |
| R1.5 合成产品纵向切片 | 以合成身份和确定性能力验证教师创建、学生实践、提交、复核、反馈与补正；核实现有 Web 主路径 | 可复现演示、测试和限制记录 | 关键状态可回放；错误和未知状态不伪装成功；界面与接口契约一致 |
| R2 专家走查 | 邀请教师/领域人员检查任务效度、学生责任、证据解释和复核负担 | 反馈记录、任务/流程修订和决策 | 说明保留、修改或停止的依据；不把意见写成学习效果 |
| R3 有条件的小范围验证准备 | 制定告知、授权、最小化、去标识化、数据管理和退出方案；依规申请必要审批 | 研究治理材料与可执行方案 | 取得所有必要批准后方可接触真实参与者或研究数据 |
| R4 证据复盘与选择性扩展 | 评估任务、过程证据和迁移设计是否有效，再决定是否增加模型、执行、任务族或产品能力 | 继续、调整或停止的书面决策 | 新能力有独立需求、规格、风险控制、授权和验证证据 |

近期顺序以 B0 为前置，随后并行准备 R1 任务设计和 R1.5 合成主路径；二者均达到可审查状态后，再进入专家走查。实际进入 R2/R3、使用真实模型或代码执行均不能由本计划自动授权。

## 七 预期成果

项目成果按证据成熟度逐步形成：

- 一套有来源、有版本、有验证规则的职业任务设计方法和首个任务包。
- 一份能被审查和推翻的研究方案，区分基础能力、协作过程、任务结果与迁移表现。
- 一个服务于任务组织、学生实践、提交、教师复核和补正的 Studio 合成原型及其可复现证据。
- 在获得相应批准后形成的专家意见、非计分验证材料或研究结果，并完整说明样本、方法、限制和适用范围。
- 经证据支持后形成的教学建议、论文、竞赛材料或产品扩展方案。竞赛、发表和商业转化是可选应用路径，不作为研究有效性的替代证明。

项目不预先承诺市场规模、学校采纳、学习提升、职业能力提升或 AI 替代比例。

## 八 项目分工与治理

| 角色 | 主要责任 |
| --- | --- |
| 项目负责人 | 确认研究优先级、任务范围、资源投入、范围变更和对外结论 |
| 教师/领域顾问 | 审查职业任务来源、教学目标、验证规则、学生责任和复核负担 |
| 研究成员 | 设计比较条件、证据定义、分析方法、研究治理和限制说明 |
| 产品与工程成员 | 按已确认范围维护原型、接口、测试、版本和可复现记录 |
| 学校或研究管理方 | 在涉及真实学生、课程或数据前审查必要告知、授权和管理流程 |

所有重要产品行为、研究范围和安全边界应由对应的 Active 决策、规格或研究材料记录。本计划概述项目路线，不取代具体产品规范、技术规范、安全规格或研究审批。

## 九 数据、安全与伦理边界

- 默认使用合成身份、合成任务和非真实学生数据；真实数据只有在明确目的、授权、最小化和保护措施到位后才能单独进入。
- 教学运营数据与研究数据分开管理。运行记录不会自动成为研究数据，研究使用必须有独立依据和治理流程。
- 不采集全桌面、私人目录、无关应用、真实凭据或不必要的个人信息；模型密钥不进入学生客户端。
- 不在安全验证未通过前运行学生或外来代码，不将控制面服务当作代码执行沙箱。
- 不向学生自动输出未经验证的成绩或能力画像，不把过程信号用于作弊判定。
- 对外报告区分已实现、已测试、已验证、计划中和未知；说明证据日期、环境与限制。

## 十 主要风险与应对

| 风险 | 应对方式 |
| --- | --- |
| 任务与真实职业工作脱节 | 邀请教师或领域人员审查来源、难度、产物和验证规则 |
| 最终结果被误当作学习证据 | 将 Outcome、Process 与 Transfer 分开定义和报告 |
| 过程日志被过度解释 | 仅记录任务必要事实，明确不可观察边界，由教师作教学判断 |
| 原型或合成测试被误当作正式产品 | 标注数据类型、运行日期、环境及未验证能力 |
| 产品范围过宽、工程先于研究 | 先完成一个任务族和闭环；扩展必须经过阶段门和负责人决策 |
| 真实代码或数据带来安全、隐私风险 | 单独规格、审批和验证；未关闭 Gate 前不启用 |
| 教师复核负担过高 | 通过走查评估证据是否足以支持动作，并删除低价值字段 |

## 十一 项目完成与扩展判断

一个阶段只有在预先写明的产物和退出条件满足、证据可复核且限制清楚时，才能判定通过。代码存在、测试通过、界面可展示或文件齐全，都不能单独证明用户价值、研究有效性或真实场景适用性。

项目可以继续、调整或停止。若任务来源不可靠、结果验证规则无法解释、教师复核成本不可接受、过程事实与研究问题无关，或迁移设计无法成立，应先修改研究和任务设计，而不是通过增加功能掩盖问题。

每次扩展至少回答：它服务于哪个任务和研究问题；增加了什么可观察、可验证的证据；需要谁授权；会带来什么成本、安全和隐私风险；成功与停止的判定条件是什么。

4. 是否具备开展专家走查或非计分验证所需的人员、时间、场地和治理条件。
