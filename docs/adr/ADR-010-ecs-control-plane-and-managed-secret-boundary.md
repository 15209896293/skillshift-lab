# ADR-010 ECS 控制面与托管密钥边界

## Status

Accepted（2026-09-24；项目负责人授权主控 Agent 选择当前最优部署方向；不授权立即部署）。

## Context

SkillShift 已选择学校统一付费的 DeepSeek 托管合成探针，并已建立模型、预算和失败关闭的本地契约。现有 Ubuntu ECS 已安全初始化，但未部署业务端口、Docker、模型密钥或学生代码。

当前最优目标不是自建本地大模型或把小型 ECS 改造成执行沙箱。项目需要的是一个轻量、安全、可审计的控制面：将来托管平台 API、学校模型档案、预算许可、凭据引用、任务/提交元数据和教师/学生界面后端。

## Decision

1. 现有 ECS 被选为未来 R0 **平台控制面**的首个部署目标：API、模型网关、预算许可、任务/提交元数据与教师 Web 后端可以运行于此。
2. ECS 不运行本地大模型、不执行任意学生代码、不充当学生 Workspace、浏览器自动化或通用 Shell。Foundation Spike 的执行能力仍与该控制面隔离。
3. DeepSeek API Key 必须保存在与 ECS 服务身份绑定的**托管密钥服务**中；应用只获得短时解析结果。禁止 Key 写入 Git、环境配置文件、数据库、客户端、日志、Artifact、systemd unit 或聊天内容。
4. 控制面先采用“单个受限 API 服务 + 托管密钥服务 + 持久预算/元数据存储”的形态。真实多用户运行时使用持久关系数据库；当前内存预算许可仅用于本地测试，不能部署为账本。
5. 部署顺序固定为：本地 API 契约与安全测试 → 服务身份/密钥服务/持久账本配置 → 仅合成 DeepSeek 探针 → 监控与费用核对 → 再讨论教师界面、身份与非计分试用。

## Consequences

- 不购买 GPU、不自建本地大模型，避免在 R0 初期承担显卡、模型运维、许可和推理稳定性成本。
- 现有 ECS 足以成为轻量控制面候选，但不代表已满足生产容量、高可用、合规或真实课堂要求。
- 真实部署仍需要独立的云账户权限、托管密钥服务、数据库、网络入口、日志保留和运维配置；本 ADR 不执行这些动作。
