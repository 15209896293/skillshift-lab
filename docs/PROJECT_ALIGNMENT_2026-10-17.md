# SkillShift 项目对齐基线（2026-10-17）

## 状态、效力与用途

- 状态：**Active（项目治理与当前工作入口）**。
- 生效范围：项目定位、文档导航、证据表述与近期工作顺序。
- 不授权：真实模型调用、学生或外来代码执行、真实学生数据、研究招募、生产部署、身份接入或任何功能开发。
- 不替代：已确认的 R0 产品、技术和质量规范；涉及具体产品行为时，仍以相应 Active 决策和规范为准。

本文件解决的是“下一位负责人或开发者先读什么、当前项目在做什么、哪些材料只能作历史参考”。它不改写 `wenben/` 中的计划书，也不把历史测试、原型或研究构想表述为当前已验证事实。

## 一句话定位

> SkillShift 研究 Agent 进入职业任务后，学习者的基础能力如何影响其协作中的理解、验证、纠错与接管，以及这些过程是否与后续可迁移能力有关；SkillShift Studio 是组织任务、过程证据与教师复核的研究基础设施。

因此，项目不以自研通用 Agent、取代 Codex/Cursor、阻止外部 AI，或建设完整 LMS 为目标。

## 当前阶段

当前处于 **R0/R0.5：合成原型、证据边界与研究最小闭环准备阶段**。项目还没有进入正式课堂产品、真实 Agent 对比实验或生产系统建设。

| 方面 | 当前可确认状态 | 不可据此推断 |
| --- | --- | --- |
| 研究框架 | 已形成 Foundation—Process—Transfer 的问题框架与教授审阅稿 | 已有学习效果、职业能力或原创性结论 |
| Studio 流程 | 本机合成的教师创建—学生协作—提交—复核—补正流程与 React 原型存在 | 已通过真实课堂、真实用户或生产验收 |
| Agent | 当前实现以确定性/脚本化引导为主 | 已接入或评估真实 LLM/Agent 能力 |
| 执行环境 | Foundation Spike 为独立、部分验证的安全研究切片 | 可以运行学生或外来代码 |
| 测试证据 | 2026-09-26 有本机合成流程的历史记录 | 当前 10 月源码仍通过、或系统可复现运行 |
| 数据与部署 | 合成身份、合成任务、loopback/内存原型 | 持久化、认证、真实数据、部署或研究采集已具备 |

## 当前唯一主线

近期采用“**研究驱动的窄产品路线**”，而不是通用 Workspace 扩张：

```text
一个版本化职业任务族
        ↓
Foundation 条件 ──→ 协作过程（理解、验证、纠错、接管） ──→ Transfer
        ↑                         ↓                                  ↓
   学习者起点能力              Outcome（辅助结果）                主要研究结果

Agent Capability：作为任务条件与能力边界校准，不作为唯一终点
```

首个任务族尚未冻结。Python + CSV 数据处理/异常诊断和 SQL/数据库诊断都是候选；在任务来源、参考解、负例、确定性验证器和迁移变体确定前，二者都不能称为正式 Benchmark。

## 当前架构边界

```text
研究层：Foundation / Agent Capability / Collaboration Process / Transfer
                         ↓
Studio：教师任务与复核 ── 合成控制面 ── 学生项目工作区原型
                         ↓
后续独立 Gate：真实模型、代码执行、身份、持久化、研究数据、部署
```

- `apps/agent-first/`、`apps/teacher-web/`、`apps/student-web/`：历史合成 Harness 与控制面资产。
- `apps/studio-web/`：后续应优先收敛的 React 演示面；尚无可绑定当前源码的完整验收记录。
- `apps/student-studio/`、`execution/`：未来本机执行的安全 Spike，不是学生执行器。
- `fixtures/`：候选任务输入，不是已接受的唯一任务事实来源。

## 文档与事实来源

### 开发前的最小阅读顺序

1. 本文件：当前阶段、工作顺序与停止边界。
2. `AGENTS.md`：操作规则、证据和安全要求。
3. `docs/product/R0_PRODUCT_REPOSITIONING_DECISION.md`：已确认的产品定位。
4. 与任务直接相关的 Active 产品、技术、质量规范和已确认 ADR。
5. 有日期的状态快照、交接记录、`specs/` 与 `artifacts/`：只按各自日期和状态使用。

### 文件状态判定

| 类别 | 可作为什么 | 不能作为什么 |
| --- | --- | --- |
| Active 决策/规范 | 当前范围、产品行为、技术与质量边界 | 已实现或已验证的证明 |
| Snapshot / Handoff | 某个日期的现场状态和续办线索 | 当前版本的自动证明 |
| ADR | 已决/被否决/待决架构理由 | 自动授权实现 |
| `specs/` | 单项任务的目标与验收约束 | 高于 Active 决策的路线来源 |
| `artifacts/` | 特定日期、特定环境下的证据 | 普适产品或教育结论 |
| `wenben/`、V3.0 总纲、早期架构 | 长期愿景、历史假设和背景 | 当前 R0 的直接实施命令 |

当资料冲突时：先报告冲突；产品行为遵循 Active R0 决策，历史文件不以“更新日期较晚”自动获得更高优先级。

计划书版本与使用边界见 [`PROJECT_PLAN_VERSION_INDEX_2026-10-17.md`](PROJECT_PLAN_VERSION_INDEX_2026-10-17.md)。

## 近期工作顺序

### 阶段 B0：资产与证据基线（所有后续工作的前置）

目标是把“现有文件”变成可审计的项目基线，而不是马上增加功能。

1. 列出应保留的源代码、测试、规格、Artifact、设计稿和历史文档；明确 `node_modules`、`dist`、缓存等可重建现场物的边界。
2. 将当前 Git 工作区、运行时版本、未跟踪资产和历史 Word 归档移动记录为一个状态快照。
3. 明确一个主前端载体；建议以 `apps/studio-web/` 为后续演示面，旧静态页面标为 Harness。
4. 基线冻结后，才重新建立“当前版本”的静态检查、测试、build/lint、API/前端主路径和有限浏览器证据。

### 阶段 R1：研究最小闭环准备（需负责人确认首个任务族）

1. 冻结一个职业任务族及其职业来源。
2. 建立任务版本、参考解、负例、确定性验证器与至少两套迁移变体。
3. 把 Foundation、Agent 条件、过程事件与 Transfer 指标写成可证伪的研究设计；不以平台日志直接推断能力。
4. 只开发服务于上述设计和教师走查的最小 Studio 功能。

### 阶段 R2：专家走查与非计分小范围验证（需独立授权）

先做教师/领域专家对任务效度、复核负担和过程解释的走查；真实学生、研究数据使用和任何结论发布须单独完成告知、授权、最小化与去标识化安排。

### 阶段 R3：根据证据决定扩展或停止

只有当任务效度、过程解释和迁移设计都成立时，才讨论第二任务族、真实模型 Gate、持久化/身份或产品规模化。若教师复核无价值、任务不具职业代表性或过程事件不能解释 Transfer，应先修订研究/任务设计，而不是堆叠产品功能。

## 立即禁止的路线漂移

- 不把合成流程做成“产品已验收”的宣传。
- 不以旧测试结果证明当前未跟踪源码可运行。
- 不同时扩展 Python、SQL、Hadoop、Kafka、Flink 等多个任务域。
- 不先接真实模型、代码执行、登录、生产数据库或部署。
- 不把运营日志、粘贴量、相似度或低编辑量直接当作作弊或能力结论。

## 对负责人的待决事项

1. B0 后优先选择“研究最小闭环”还是“本机演示闭环”；两者不能混成无边界的平台开发。
2. 首个任务族选择 Python + CSV 还是 SQL/数据库诊断。
3. 是否将 React Studio 确认为唯一主演示面。
4. 何时、以何种研究治理方式进入教师走查或真实使用。
