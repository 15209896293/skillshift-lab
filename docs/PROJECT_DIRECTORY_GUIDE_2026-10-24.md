配套的两张架构图表达的是项目的整体愿景：研究问题产生任务，任务在 Studio 中形成过程与结果材料，分析后支持教学应用并反馈研究。它们是概念架构，不代表图中模块都已开发、验证或获准投入真实课堂。

| 架构层 | 图中想表达什么 | 项目内对应资料与资产 | 目前能确认的状态 |
| --- | --- | --- | --- |
| 研究层 Research | 研究 Agent 能力条件、人类基础能力、人机协作过程与技能迁移的关系 | [`PROJECT_ALIGNMENT_2026-10-17.md`](PROJECT_ALIGNMENT_2026-10-17.md)、[`SKILLSHIFT_PROJECT_PLAN_2026-10-24.md`](SKILLSHIFT_PROJECT_PLAN_2026-10-24.md)、`research/SKILLSHIFT_RESEARCH_DIRECTION_AI_FACULTY_REVIEW_DRAFT.md` | 已有研究问题框架与审阅稿；没有真实参与者研究结果。Benchmark、Skill Model 等图中模块不是已冻结研究产品。 |
| 数据层 Data | 承接任务、结果、必要的人机协作事实和研究数据 | `product/R0_RESEARCH_TASK_EVIDENCE_CONTRACT.md`、`fixtures/`、对应的 `artifacts/` | 有合成样例、任务契约和证据边界；任务族仍未冻结，也没有正式实验数据或已启用的 Personal Skill Memory。产品运行材料不会自动成为研究数据。 |
| 实验与产品层 Studio | 教师组织任务，学生与 Agent 协作、提交，教师复核和反馈 | `apps/studio-web/`、`apps/teacher-web/`、`apps/student-web/`、`apps/agent-first/`；对应规格在 `specs/` | 存在合成原型、流程 Harness 和前端源码；不是完整课堂产品。当前 Agent 不能据此说成真实模型能力，当前源码也缺少完整现场验收。 |

| 应用输出层 Application | 将经复核的结果用于学生实践、教师反馈及后续学校/行业应用 | 学生/教师原型、总体计划书中的长期设想 | 当前可对应的是合成教师—学生流程；学校级应用、企业可信能力画像和培养方案调整仍属长期设想，没有现实应用证据。 |

### 图中右侧流程对应的当前可执行主线

```text
明确一个职业任务族
→ 写清基础能力、协作责任、结果检查与迁移任务
→ 用合成 Studio 流程走通教师创建—学生协作—提交—复核—补正
→ 请教师/领域人员审查任务和证据是否合理
→ 取得单独授权后，才考虑真实参与者验证
```

这条主线优先于把图中所有模块都做成软件。Python + CSV 是计划中的优先候选入口，但任务来源、参考解、负例、确定性验证规则和迁移变体未齐备前，不称为正式 Benchmark；真实模型、学生数据、代码执行和部署也仍需独立授权。

### 阅读这张图时的状态标记

- **已有研究/规格材料**：有文档定义问题、边界或计划，不等于功能已实现。
- **合成原型/历史测试**：证明特定合成流程在特定日期、环境下被检查过，不等于真实课堂或当前完整产品验收。
- **候选/待验证**：仍需任务审查、研究设计、真实证据或独立授权。
- **长期设想**：包括个人技能记忆、自动能力画像、推荐引擎、企业应用等，不进入当前 R0 的事实描述。

## 文档与证据怎样区分

| 材料类型 | 能用于什么 | 不能单独证明什么 |
| --- | --- | --- |
| Active 决策/规范 | 确认当前产品行为、技术约束和质量要求 | 功能已经实现、用户价值已经成立 |
| 计划书/路线图 | 说明目标、假设、阶段和建议 | 研究结果、实际进度、预算承诺或实现状态 |
| 状态快照/交接 | 记录特定日期的观察和待办线索 | 当前版本已通过同样检查 |
| `specs/` | 定义单项工作的范围、验收和禁止项 | 任务已完成或验收通过 |
| `tests/` 与测试报告 | 说明被测范围在特定条件下的机器检查结果 | 真实课堂效果、生产安全或未覆盖场景 |
| `artifacts/` | 支持特定运行、审计或研究结论 | 超出记录日期、环境、样本和方法的普遍结论 |

## 文件放置建议

- 全项目目标与阶段路线：维护于当前总体计划书；具体开发顺序仍看项目对齐文件。
- 已确认产品决定：`docs/product/`；架构决定：`docs/adr/`。
- 未确认方案：放入相应设计材料并标记 Proposed，不混入已确认规则。
- 单项可执行工作：新建对应 `specs/` 任务目录，写明允许范围、禁止范围和验收证据。
- 测试、运行与研究证据：放入相应代码测试位置或 `artifacts/`，保留日期、环境、输入和限制。
- 原始计划、旧 Word 和历史材料：继续留在 `wenben/` 与归档目录，不为追求整齐而覆盖或删除。
