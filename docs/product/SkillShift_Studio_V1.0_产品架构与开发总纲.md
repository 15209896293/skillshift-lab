## 2. 产品一句话定位

SkillShift Studio 是一个以通用 Agent 为能力基座、面向职业教育项目实践的桌面工作软件。

它让教师能够为具体教学任务配置 Agent 的能力和权限，让学生在个人成长空间与课堂项目空间中使用 Agent 完成职业任务，并将任务产物、人机协作、验证过程和教师反馈组织成可复核的技能证据。

SkillShift Studio 不是普通聊天助手、作业监督平台、完整 LMS、个人知识库或通用 Agent 开发平台。

## 4. 我们发现的问题

### 4.1 通用 Agent 与职业教学任务相互分离

学生可以使用通用 AI 工具，但任务目标、项目材料、Agent 对话、产物、验证和教师反馈通常分散在不同工具中。

结果是：

- 学生得到了一段答案，却不一定理解任务；
- 教师无法知道 Agent 在任务中承担了什么角色；
- 项目产物与协作过程无法形成连续证据；
- AI 使用很难转化为可教、可复盘的职业实践。

### 4.2 教师无法精细配置 Agent 的任务权限

普通聊天工具通常只有“允许使用”或“不允许使用”两种粗粒度选择，无法针对不同任务规定：

- Agent 可以读取哪些材料；
- Agent 可以使用哪些工具；
- Agent 是否可以生成代码或修改建议；
- 哪些动作必须由学生确认；
- 哪些产物必须由学生解释和验证。

### 4.3 学生个人使用和正式任务使用混在一起

学生在课下自主使用 Agent 是合理且必要的，但个人学习记录不能自动等同于课堂任务证据。

如果二者不分离，可能出现：

- 学生私人内容被错误纳入教师评价；
- 任务证据与个人探索记录相互污染；
- 教师无法判断哪些内容属于正式任务；
- 学生不敢长期使用个人 Agent。

### 4.4 传统评价主要看最终结果

只看代码、报告或最终提交，无法充分回答：

- 学生是否理解任务目标；
- Agent 提供了什么建议；
- 学生是否验证了 Agent 的建议；
- 学生在哪些环节进行了判断和接管；
- 学生能否把能力迁移到新任务。

### 4.5 当前原型具备流程，但不像成熟 Agent 软件

现有 Web 原型已经验证了任务发布、提交、复核、补正和状态恢复等控制面逻辑，但仍然偏向页面和表单：

- 学生缺少统一项目工作台；
- Agent、文件、任务和验证结果没有形成强空间关系；
- 教师 Agent 尚未形成任务设计工作流；
- 个人 Agent 与任务 Agent 尚未分成产品空间；
- 桌面软件形态尚未建立。

## 5. 产品解决方案

SkillShift Studio V1.0 通过五个产品机制解决上述问题。

### 5.1 统一 Agent 工作软件

把任务、文件、对话、工具、产物、验证和反馈组织在一个项目工作区内，让学生围绕职业任务使用 Agent，而不是只在聊天窗口中获取答案。

### 5.2 教师任务级 Agent Policy

每一个课堂任务都拥有自己的 Agent Policy。教师可以配置任务允许的 Agent 能力，学生不能默认获得超出任务范围的能力。

### 5.3 个人 Agent 与任务 Agent 分区

学生首页提供个人 Agent；课堂任务进入任务 Agent。两者在界面、权限、记录和导出中区分。

### 5.4 证据链而不是监控链

系统只记录任务相关的必要事件、学生主动提交的材料、Agent 建议、学生决定、验证结果和教师反馈。

系统不通过全桌面监控、浏览器监控、隐私扫描或单一模型判断来推断作弊、努力或能力。

### 5.5 研究方法与软件闭环结合

软件不只展示功能，还要支持：

```text
任务定义
→ Agent 能力配置
→ 学生协作
→ 产物验证
→ 教师复核
→ 迁移任务
→ 技能证据组织
```

## 6. 产品价值与研究意义

### 6.1 对学生

- 获得可使用的通用 Agent 工作能力；
- 在真实任务结构中学习委托、判断、验证和接管；
- 保留项目、产物、反馈和协作证据；
- 逐步形成个人职业成长资产。

### 6.2 对教师

- 用 Agent 辅助设计教学任务；
- 为每个任务配置合适的 Agent 能力边界；
- 查看任务相关的事实和证据；
- 对学生进行反馈、补正和任务调整；
- 减少重复性任务整理工作，但保留教师决策权。

### 6.3 对学校

- 获得 AI 时代项目式教学的实践基础；
- 了解不同任务和专业对 Agent 的适配要求；
- 获得专业培养和任务设计的改进依据。

### 6.4 对研究

- 建立职业任务 Benchmark；
- 研究 Human-Agent 协作能力；
- 验证任务结果和过程证据的关系；
- 研究能力在迁移任务中的有效性；
- 形成教育动态适配的方法和数据结构。

### 6.5 对挑战杯

软件实物展示的不只是页面，而是一套可运行的方法载体：

- 有问题定义；
- 有任务模型；
- 有 Agent 权限方法；
- 有协作和验证过程；
- 有可回放的证据；
- 有研究和应用意义。

## 7. 用户与角色

### 7.1 学生

核心目标：使用个人 Agent 和任务 Agent 完成学习与职业项目实践。

学生拥有：

- 个人首页；
- 个人 Agent；
- 课堂和项目任务；
- 任务文件和产物；
- Agent 协作记录；
- 学生主动提交的说明和验证；
- Personal Skill Memory。

### 7.2 教师

核心目标：使用教师 Agent 设计任务，配置任务 Agent，查看证据并指导学生。

教师拥有：

- 教师首页；
- 教师 Agent；
- 任务设计器；
- Agent 权限配置器；
- 学生预览；
- 复核队列；
- 补正和反馈工作流；
- 任务复盘和数据导出。

### 7.3 研究人员

核心目标：在获得授权后使用去标识化研究数据，分析任务表现、Agent 能力和迁移结果。

研究人员不默认查看学生个人空间，也不直接修改教学任务。

### 7.4 系统与运营人员

核心目标：管理系统配置、模型网关、版本、预算、运行状态和安全边界。

运营人员不直接获得学生教学判断权。

## 9. 两种 Agent 空间

### 9.1 个人 Agent

个人 Agent 是学生的日常学习和成长助手。

可以支持：

- 日常问题咨询；
- 概念解释；
- 学习计划；
- 个人资料分析；
- 个人项目整理；
- 技能复盘；
- 个人作品集准备。

个人 Agent 的内容默认属于学生个人空间，不自动进入课堂评价或研究数据。

个人 Agent 可以采用接近通用 Agent 的交互方式，但文件、工具和外部服务访问必须经过明确授权。

### 9.2 任务 Agent

任务 Agent 是教师为某一个任务配置的 Agent。

任务 Agent 的能力完全由教师任务配置决定，至少包括：

- 是否允许对话；
- 是否允许读取任务材料；
- 是否允许读取指定文件；
- 是否允许生成代码或文本建议；
- 是否允许提出修改差异；
- 是否允许调用指定工具；
- 是否允许生成验证建议；
- 是否需要学生确认后才能产生下一步动作；
- 是否记录相关协作事件；
- 是否允许进入任务提交包。

默认原则：

- Agent 可以建议，不直接替学生承担最终责任；
- 文件修改、工具调用和正式产物生成必须按教师 Policy 控制；
- 学生应能接受、拒绝、修改或接管 Agent 建议；
- 教师不能把 Agent 的内部判断直接当作学生能力结论。

## 10. 教师端产品结构

### 10.1 教师首页

首页不是简单数据仪表盘，而是教师工作入口。

主要内容：

- 我的课程和项目；
- 待设计任务；
- 待复核提交；
- 待处理补正；
- 教师 Agent 快捷入口；
- 最近任务状态；
- 任务风险和缺口提醒。

### 10.2 教师 Agent 工作区

教师可以使用自然语言描述教学需求，例如：

> 为高职大数据专业设计一个 90 分钟的 Python 数据清洗任务，学生已掌握基础 Pandas，希望重点训练异常值处理和结果解释，允许 Agent 提供建议但不能直接提交最终报告。

教师 Agent 输出任务草案：

- 职业场景；
- 学习目标；
- 任务目标；
- 学生起始材料；
- 工作步骤；
- Agent 协作建议；
- 学生责任；
- 提交要求；
- 验证规则；
- 常见错误；
- 迁移任务建议；
- 教师复核要点。

教师必须审阅、修改并主动确认，才能进入发布流程。

### 10.3 任务设计器

任务设计器分为：

1. 基本信息；
2. 职业场景；
3. 学习目标；
4. 项目材料；
5. 学生责任；
6. 提交要求；
7. 验证规则；
8. Agent Policy；
9. Transfer 任务；
10. 隐私与风险说明；
11. 学生预览；
12. 发布确认。

### 10.4 Agent Policy 配置器

教师通过能力卡片和权限模板配置任务 Agent，而不是直接编写复杂代码。

建议的 T0 配置项：

| 配置项 | 例子 |
|---|---|
| 对话 | 允许解释、允许追问、限制回答范围 |
| 文件 | 只读任务材料、允许读取指定目录 |
| 生成 | 生成思路、生成代码片段、生成报告结构 |
| 修改 | 只生成差异、学生确认后应用 |
| 工具 | 无工具、固定验证器、指定数据分析工具 |
| 验证 | 允许提出验证步骤、不能替代学生解释 |
| 记录 | 记录 Agent 建议、学生决定和验证结果 |
| 模型 | 合成 Agent、指定真实模型、教师审批模型 |
| 预算 | 每人轮次、Token、时间或费用上限 |

### 10.5 复核与补正工作区

教师查看：

- 学生提交包；
- 任务版本；
- 产物摘要；
- 学生说明；
- Agent 协作事件；
- 验证结果；
- 学生接受、拒绝或接管记录；
- 失败和重试；
- 历史补正关系。

教师动作：

- 认可；
- 请求说明；
- 请求补正；
- 标记环境问题；
- 添加教学反馈；
- 关闭本轮任务。

这些动作不自动等价于成绩、作弊或能力判断。

### 10.6 教师任务复盘

教师 Agent 可以辅助生成：

- 常见问题摘要；
- 任务难度问题；
- Agent 权限是否过宽；
- 哪些步骤需要增加说明；
- 哪些学生在迁移任务中需要支持；
- 下一次任务的修改建议。

最终修改和发布仍由教师确认。

## 11. 学生端产品结构

### 11.1 学生首页

学生登录后先进入首页，而不是直接进入某个课堂任务。

首页包括：

- 个人 Agent 入口；
- 最近项目；
- 课堂任务入口；
- 待处理任务；
- 最近反馈；
- 技能成长摘要；
- 个人成果；
- 账户和隐私设置。

### 11.2 个人 Agent 工作区

个人 Agent 页面应接近通用 Agent 软件，而不是课堂问答页面。

包含：

- 多轮对话；
- 文件和资料导入；
- 个人项目空间；
- Agent 计划；
- 工具和操作卡片；
- 生成内容预览；
- 学生确认和撤销；
- 个人记忆开关；
- 资料删除和导出。

个人 Agent 的所有外部访问和文件权限必须可见、可撤销。

### 11.3 课堂任务列表

课堂任务是独立导航入口，展示：

- 课程或项目；
- 任务标题；
- 任务状态；
- 截止时间；
- Agent 使用规则；
- 当前提交版本；
- 教师反馈；
- 待补正事项。

### 11.4 学生项目工作台

建议采用四区布局：

```text
左侧：任务与文件导航
中间：项目材料、代码或产物编辑区
右侧：任务 Agent 对话、计划和建议
底部：验证状态、事件时间线和提交区
```

核心区域：

- 任务说明；
- 职业场景；
- 文件树；
- 编辑器或文档区；
- Agent 对话；
- Agent 建议卡片；
- 修改差异；
- 验证器结果；
- 学生解释；
- 提交和版本。

### 11.5 学生提交与反馈

提交前学生需要看到：

- 任务目标是否完成；
- 必要产物是否齐全；
- 验证是否通过或仍有风险；
- 学生说明是否完成；
- Agent 建议是否已经确认或拒绝；
- 哪些内容会进入提交包。

教师补正后，学生进入同一任务的下一版本，不创建无法关联的新任务。

## 12. Personal Skill Memory

### 12.1 V1.0 目标

V1.0 不声称已经建立完整三年成长档案，但必须展示可运行的个人技能记忆原型。

### 12.2 记录对象

- 项目经历；
- 任务版本；
- 学生产物；
- 验证结果；
- 学生解释；
- 教师反馈；
- Agent 协作摘要；
- Transfer 任务表现；
- 个人技能标签；
- 个人成果包。

### 12.3 记录原则

- 学生知道记录了什么；
- 学生可以查看、导出和请求删除；
- 个人 Agent 数据默认不进入教师任务评价；
- 研究数据与运营数据分离；
- 任何能力解释都必须回到具体证据，不由模型单独下结论。

## 13. Agent、LLM 与工具架构

### 13.1 分层结构

```text
用户界面
    ↓
Studio Agent Orchestrator
    ↓
Agent Policy + Context Builder
    ↓
Agent Adapter
    ├── Synthetic Agent
    ├── Hosted LLM
    └── Future Providers
    ↓
Tool / Artifact / Verification Boundary
```

### 13.2 合成 Agent

用于：

- 产品开发；
- 自动化测试；
- 无网络演示；
- 状态流验证；
- 错误和失败场景验证。

合成回答必须在界面上明确标记，不得包装成真实模型能力。

### 13.3 真实 LLM

真实 LLM 用于：

- 受控产品演示；
- 教师任务设计辅助；
- 学生个人 Agent 体验；
- 任务 Agent 的指定能力验证。

真实模型接入必须通过服务端网关和预算/数据边界，不在学生客户端保存密钥。

### 13.4 Agent 行为原则

- Agent 可以解释、计划、建议和提出修改；
- 关键写入和工具动作按 Policy 控制；
- 学生可确认、拒绝或接管；
- 教师可以规定任务级能力；
- 系统记录必要的任务相关事件；
- Agent 不自动产生学生能力结论；
- 降级和不可用状态必须可见。

## 22. 验收标准

### 22.1 产品验收

- 教师和学生通过统一软件入口进入不同工作区；
- 个人 Agent 和任务 Agent 明确分开；
- 教师可以为每个任务配置 Agent Policy；
- 学生可以看到任务允许和禁止的能力；
- 教师 Agent 可以生成任务草案，但不能绕过确认自动发布；
- 学生可以完成一个 Python 数据清洗任务闭环；
- 教师可以查看提交和任务相关证据；
- 反馈和补正可以形成版本关联；
- Personal Skill Memory 可以展示一条完整证据。

### 22.2 工程验收

- 页面使用统一设计系统；
- API 对象和版本明确；
- Agent Adapter 可以替换合成 Agent 和真实 LLM；
- 错误、加载、空状态和降级状态可见；
- 任务 Agent 权限不能由客户端自行扩大；
- 关键写入和工具调用有确认或审计；
- 现有关键测试不因 UI 重构被绕过；
- 代码执行仍受独立安全 Gate 约束。

### 22.3 研究验收

- 任务目标和验证规则清晰；
- Agent 使用条件可复现；
- 过程事件与任务、用户、版本关联；
- 结果、过程、迁移分开解释；
- 不把合成结果包装为真实教育效果；
- 不输出 AI 替代率或未经实验支持的能力结论。

## 26. 关键原则

1. 通用 Agent 是能力基座，SkillShift 的差异在任务、权限、证据和教育工作流。
2. 教师为每个任务配置任务 Agent 能力，学生不能获得未经允许的任务权限。
3. 个人 Agent 与任务 Agent 必须分区，个人成长内容不自动成为课堂评价证据。
4. Agent 可以建议和协作，但不能替学生承担最终解释和验证责任。
5. 产品软件化优先于继续堆叠简单网页功能。
6. 先完成一个完整 Golden Path，再扩展多任务、多专业和学校部署。
7. 合成 Agent、真实 LLM、代码执行、真实身份和部署分别验证，不相互冒充。
8. 每个产品能力都必须能回答：解决什么问题、产生什么证据、有什么限制。
