## 1. 项目主线

SkillShift 是面向 AI Agent 时代职业任务变化、Human-Agent 协作能力与职业教育动态适配的长期研究与应用项目。

当前核心研究命题是：

> 当 Agent 参与职业任务后，任务结构、人类责任、验证要求与能力迁移方式如何变化；职业教育应如何据此重新设计任务与评价。

SkillShift Studio 是这项研究的实践、证据与产品化载体，不是项目全部，也不以模型能力本身与 Codex、Claude、Cursor、Trea 等通用 Agent 产品竞争。

Studio 当前不得被定位为：

- 作业监督或作弊检测平台；
- 普通 AI 聊天工具；
- 完整 LMS；
- 通用 Agent 开发平台；
- 已经可以评价学生能力的自动评分系统。

正式项目主线继续保持职业技能与 Human-Agent 协作方向。儿童、幼儿、小学 Agent 方向未进入当前正式项目文件，不是本阶段开发范围。

## 4. 项目负责人已经表达的产品意图

以下内容已经在项目讨论中得到负责人明确表达，但其中部分尚未与所有 Active 文档完成一致性修订。下一窗口应先将其转化为正式、可审查的产品决策，再据此开发。

1. Studio 应以通用 Agent 能力为基座，使用体验要接近成熟 Agent 软件，而不是简单表单网站。
2. 同一软件根据登录账号进入教师端或学生端。
3. 学生端包含个人 Agent 与课堂任务空间；个人 Agent 供学生课下自主使用，不强制与课堂任务混合。
4. 教师端需要教师 Agent，辅助教师设计、发布和复盘任务，同时允许教师详细编辑任务。
5. 每项课堂任务的 Agent 能力与权限由教师配置，学生不得自行扩大权限。
6. 学生进入首页后，课堂任务应有独立入口和项目工作台。
7. Personal Skill Memory 在 V1.0 先形成成熟的数据结构与界面原型，长期成长价值以后续真实证据验证。
8. Studio 需要成为成熟、高完成度的软件原型，并能支撑挑战杯的软件实物展示。
9. UI 可以参考 Trea 的空间组织、信息密度和 Agent 工作区体验，但不得复制其品牌、视觉资产或产品定位。

推荐的权限收口方式：

> 教师可在每个任务中，从系统审核过的能力白名单、工具白名单和数据范围中进行组合配置；教师不能绕过平台安全上限开放任意宿主机权限。

该方案同时保留“逐任务配置”的产品意图与安全、测试和研究可比性。

## 5. 当前存在的权威冲突

开始全面 UI 或后端开发前，必须明确处理以下冲突：

### 5.1 Agent Policy 冲突

- `docs/product/R0_PRODUCT_REPOSITIONING_DECISION.md` 当前写明：R0 由教师选择固定协作模式，不开放自定义权限编排。
- `docs/product/SkillShift_Studio_V1.0_产品架构与开发总纲.md` 写明：教师为每个任务配置 Agent 的能力与权限。

不得静默选择其中一份。建议建立新的、范围明确的 R0.5 决策：R0.5 允许教师在平台白名单内进行逐任务配置；底层危险权限、安全上限和数据边界不可由教师解除。

### 5.2 首条交付形态冲突

- 早期 Agent-first 闭环以平台内文本协作和学生主动提交为主，不开放本机执行。
- 后续产品意图要求项目型工作台、文件上下文、验证器和接近通用 Agent 软件的体验。

建议保留早期闭环作为控制面和失败恢复 Harness；R0.5 在其上增加一个受控任务工作区，不将早期页面继续扩展为最终 UI。

### 5.3 研究优先级与软件观感冲突

研究主线要求先形成可验证任务和方法；负责人同时要求软件具备成熟观感。两者不应互相替代：

- 研究先冻结一条任务、验证和迁移结构；
- UI 只围绕该 Golden Path 设计高完成度页面；
- 不先建设覆盖所有专业和所有功能的空壳平台。

## 10. 首个任务族

首个任务族建议冻结为：

> Python + CSV 数据清洗、异常诊断与结果验证。

原因：

- 与数据技术、软件技术和数字化职业任务相关；
- 输入、输出、异常类型和验证规则可冻结；
- 可以设计正确结果相同、协作与验证质量不同的情形；
- 可以复用现有数据清洗验证思路；
- 比自由代码项目更容易建立受控执行和确定性证据；
- 适合 Foundation—Agent—Transfer 三段研究结构。

首任务必须包含：

| 部分 | 最低要求 |
| --- | --- |
| Foundation | 限制或不使用 Agent，检查基础理解和规则识别 |
| Agent | 使用固定版本任务 Agent，完成数据清洗、诊断、验证和解释 |
| Transfer | 更换数据、字段、异常组合或约束，减少提示或改变 Agent 条件 |
| Verifier | 对输出文件、行数、字段、异常清单和不变量做确定性检查 |
| Human responsibility | 学生确认目标、选择方案、解释关键决策、处理验证失败并承担最终提交责任 |
| Evidence | 任务版本、Agent 条件、关键操作、验证结果、学生解释、教师反馈和迁移表现 |

不要把聊天次数、提示词长度或使用时长直接解释为能力。

## 12. R0.5 验收标准

只有同时满足以下条件，才能称“R0.5 Golden Path 通过”：

### 12.1 产品验收

- 教师能创建并发布一个冻结的 Python/CSV 任务；
- 教师能从平台白名单配置任务 Agent；
- 学生能明确进入指定任务工作台；
- 学生能使用真实 Agent 处理任务上下文；
- 学生能运行确定性验证并看到可理解结果；
- 学生能提交产物、解释与验证引用；
- 教师能查看证据并确认或要求补正；
- 学生能补交并完成迁移任务；
- 个人 Agent 与任务 Agent 的记录和权限不混用。

### 12.2 工程验收

- 关键对象、状态、版本和错误语义有明确契约；
- 至少包含静态、单元、集成和一条浏览器纵向测试；
- 合成 Agent 与真实 Agent 在界面和日志中明确区分；
- 验证器、模型、平台和用户错误不混为同一失败；
- API Key 不进入学生客户端；
- 任务目录外文件和危险工具默认不可访问；
- 已知限制和未验证边界在产品与报告中可见。

### 12.3 研究验收

- 任务、数据、Agent 条件、验证器和指标版本可追溯；
- 有正例、负例和至少一个 Agent 失败案例；
- Foundation、Agent、Transfer 的比较逻辑明确；
- 原始事件、派生指标和研究解释分离；
- 不输出 AI 替代率，不把单次结果当作学生能力或普遍教育结论；
- 数据最小化、告知、退出、删除和研究授权边界明确。

---

## 13. 当前明确不做

R0.5 Golden Path 期间暂不建设：

- 多专业任务市场；
- 企业招聘或人才推荐；
- 完整 Personal Skill Memory 长期算法；
- 学校组织与复杂权限后台；
- 正式成绩自动生成；
- AI 替代率或职业淘汰预测；
- 全桌面监控、浏览器历史采集或外部 AI 检测；
- 任意学生代码的生产执行沙箱；
- 多模型排行榜；
- 大规模并发、商业化计费和正式生产部署；
- 未经批准的真实学生实验。

这些内容可以保留在长期规划中，但不得成为当前纵向闭环的前置条件。

## 14. 竞赛成果映射

Studio 开发必须同步服务研究和挑战杯证据链：

| 软件或实验产物 | 对应研究/竞赛价值 |
| --- | --- |
| 冻结职业任务与版本 | 研究对象和可复现基础 |
| Agent Policy | 不同协作条件的实验控制 |
| 确定性 Verifier | 不依赖 LLM 自评的任务结果证据 |
| 学生解释与接管 | 人类责任和验证能力证据 |
| Transfer 任务 | 区分任务完成与能力迁移 |
| 教师复核与补正 | 教育适配和教师可行动性证据 |
| 失败案例与限制报告 | 科学性、可信度与适用边界 |
| Studio 软件实物 | 方法的实验载体和应用证明 |

比赛叙事不得退化为“我们做了一个 Agent 平台”。候选科技成果应逐步收敛为：

> 一种基于任务有效性、确定性验证、Human-Agent 责任证据与迁移表现的职业能力评价及教学任务适配方法。

该表述目前仍是研究方向，不是已经验证的发明成果。
