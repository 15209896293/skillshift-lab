# V2.2 项目快速理解

本节面向第一次接触项目的教师、评审者和开发人员。后续原有完整计划、研究方案与工程文档全部保留，本节只负责在 5–10 分钟内讲清“为什么做、做什么、怎样落地、接下来先验证什么”。

## 一、项目最核心的现实矛盾

SkillShift 不再假定 Agent 会在短期内全面进入正式课堂。现实中，课程、考试、考证与教学管理变化较慢，而 Agent 已经快速改变真实数字工作的完成方式。由此产生的核心问题不是“如何强迫课堂马上使用 Agent”，而是：学生在现有体系中学到基础技能以后，怎样继续把这些基础迁移为 Agent 时代真实的人机协同职业能力。

| **现实层** | **当前状态** | **SkillShift 的处理** |
|----|----|----|
| 正式课堂/考试 | 仍以基础知识、独立操作、既有考核为主 | 不替代、不强行改变，保留 Foundation Track |
| 行业/个人实践 | Agent 已能承担代码、终端、配置、数据处理等大量工作 | 建立 Agent Track，训练委托、判断、验证、接管 |
| 两者之间 | 存在时间差和能力断层 | 通过双轨配对任务研究并训练“能力迁移” |

## 二、产品一句话

SkillShift Lab 是一套连接“学校基础技能学习”与“Agent 时代工作方式”的双轨实训与能力迁移平台：第一阶段以课余/第二课堂和学生自主实践为主，Foundation Track 确认学生自己会什么，Agent Track 允许学生充分使用智能体完成更复杂的真实任务；平台通过真实环境、可验证结果、迁移任务和关键协作事件分析两条轨道之间的能力迁移。

## 三、双轨模型

| **轨道** | **目标** | **典型规则** | **主要回答** |
|----|----|----|----|
| Foundation Track 基础能力轨 | 确认专业基础和独立操作能力 | 无 Agent / 受限 AI；贴近课程、考试、考证 | “学生自己会什么？” |
| Agent Track 人机协同轨 | 训练面向未来工作的复杂任务能力 | 允许/鼓励 Agent；任务同步提高复杂度 | “学生能否把基础迁移为人机协同能力？” |
| Transfer / Research 迁移层 | 比较两轨表现与后续迁移 | 等价任务、错误建议、迁移/后测 | “AI提高的是完成表现还是形成了可迁移能力？” |

## 四、产品只做三件核心事情

| **核心能力** | **解决的问题** | **首版形态** |
|----|----|----|
| 1\. 双轨任务设计 | 旧课程技能如何变成“基础任务 + Agent职业任务”配对任务 | Task Template + Task Graph + Evidence Contract |
| 2\. 多环境人机实训 | 学生在机房、自己的电脑、或没有个人电脑时都能完成任务 | 统一 Web 工作区 + 可切换执行后端 |
| 3\. 真实结果与协作评价 | 不只看答案，还看真实系统状态与关键人机决策 | Hidden Verifier + Task-scoped Telemetry + Report |

## 五、面向现实设备条件的统一使用方式

学生端采用“Web/PWA 为统一入口 + 可选 Personal Node 本地执行代理”的架构。学校机房不需要为每台电脑安装完整软件，只要浏览器能够访问平台即可；有个人电脑的学生可安装轻量 Personal Node，把自己的电脑变成长期学习节点；没有个人电脑的学生由学校/项目提供 Managed Sandbox，共享远程计算资源。三种方式使用同一套账号、任务、Agent 与报告，不分裂成三个产品。

| **使用场景** | **学生端** | **任务执行位置** | **适用人群** |
|----|----|----|----|
| 学校机房 | 浏览器/PWA | 学校执行节点或远程 Managed Sandbox | 所有学生，尤其无个人电脑者 |
| 学生自己的电脑 | 浏览器/PWA + SkillShift Personal Node | 学生本机 Docker/WSL/受控工作区 | 有电脑、希望长期积累个人环境者 |
| 临时远程使用自己的电脑 | 浏览器 → Personal Node 安全通道 | 学生自己的电脑 | 可选桥接；不依赖通用远程桌面作为产品核心 |

## 六、教师端、学生端、后台控制台如何分工

| **端** | **核心职责** | **不承担的职责** |
|----|----|----|
| 学生工作区 | 基础轨/Agent轨任务、Terminal/Editor、Agent协作、Evidence、提交、个人反馈 | 不负责课程管理和系统运维 |
| 教师工作台 | 课程/班级、双轨任务发布、任务重构、结果/过程报告、教学反馈 | 不直接管理服务器底层资源 |
| 后台控制台 | 账号与角色、执行节点、Sandbox队列、Agent模型/配额、任务/Verifier版本、系统健康与审计 | 不替教师做教学评价 |
| 研究工作台（后续） | 只访问符合授权的去标识化数据、条件配置、数据版本与研究导出 | 不直接访问学生身份数据 |

## 七、宏观技术架构：控制面、执行面、数据面

| **架构面** | **核心组件** | **职责** |
|----|----|----|
| 交互层 | Student Web/PWA、Teacher Web、Admin Console | 所有角色统一通过 Web 访问；个人电脑仅额外安装可选 Node |
| 控制面 Control Plane | Auth/RBAC、Course/Assignment、Task Engine、Session Orchestrator、Agent Gateway、Scheduler | 决定“谁在什么时候执行什么任务、使用哪个 Agent、落到哪个执行节点” |
| 执行面 Execution Plane | Managed Sandbox、School Node、Personal Node、Terminal/Editor/Data Services | 真正运行代码、数据库、Linux、大数据组件；不同后端通过统一 Execution Adapter 暴露能力 |
| 评价面 Evaluation Plane | Evidence Collector、Hidden Verifier、Report Engine | 在 Agent/学生权限之外验证真实结果，并生成报告 |
| 数据面 Data Plane | Operational DB、Event Store、Artifact Store、Research Export | 教学运行数据与科研数据分离；原始事件不可静默覆盖 |

## 八、远程控制软件的定位

ToDesk、向日葵等通用远程控制工具可以在早期试点中作为“应急桥接”，但不应成为 SkillShift 的核心依赖。原因是它无法提供结构化任务事件、环境能力声明、最小权限、统一 Verifier 和可复现研究数据，同时会引入隐私、网络、NAT、防火墙与账号管理问题。正式架构采用 Personal Node：由学生主动安装，只开放指定 SkillShift 工作区和任务能力，通过出站加密长连接连接服务器，不默认暴露完整桌面。

## 九、现在开发到什么程度才算“开始”

当前不是“大平台全面开发”阶段，而是“方向冻结、P0 证据验证、单任务垂直切片”阶段。先证明真实旧任务会被 Agent 快速击穿、双轨重构有教育价值、统一多后端架构能跑通，再扩展 6 个任务和真实试点。

| **阶段** | **先做什么** | **通过条件** |
|----|----|----|
| P0-A 传统任务 Agent 冲击审计 | 收集 10–20 道现有真实实训，测试主流 Agent 可直接完成程度 | 形成可复现数据，不预设“替代率”结论 |
| P0-B 教师访谈 | 用真实审计结果访谈 3–5 位教师 | 至少出现明确的任务重构/课外实训需求，而非礼貌性认可 |
| P0-C 双轨任务重构 | 选 3 道典型旧题，设计 Foundation + Agent 配对任务 | 教师确认仍保留原教学目标且 Agent 轨有真实新增价值 |
| P0-D 小样本课外 Pilot | 5–20 名学生，优先第二课堂/创新训练场景 | 事件模型可解释、学生可用、设备条件能覆盖 |
| M1 单任务垂直切片 | 教师发布→学生任务→Agent→执行→Verifier→提交→报告 | 端到端稳定；再决定 6 任务 MVP |

## 十、V2.2 核心转向：第二课堂 / 课余实践优先

SkillShift 的第一落地入口正式从“等待 Agent 进入课堂”转为“先服务课余/第二课堂的职业能力迁移”。正式课堂继续承担基础知识、考试和考证要求；SkillShift 面向愿意提前接触 Agent 工作方式的学生，提供结构化任务、真实环境、Agent 协作、结果验证和迁移训练。这样，项目不依赖课程改革即可启动，也不会与现有教学体系形成正面冲突。

这一转向不是把项目做成普通 AI 培训。平台不以“教会几个 AI 工具”为目标，而是要求学生把已经学过的 Python、SQL、Linux、数据库和数据工程基础迁移到更复杂的 Agent 协同任务中，并通过 Hidden Verifier、迁移任务和真实交付物证明结果。

| **层级** | **主要职责** | **SkillShift 的关系** |
|----|----|----|
| 正式课堂 / 考试 | 建立基础知识、基本操作和现有培养方案要求 | 提供 Foundation 基线，不要求立即改变 |
| 课余 / 第二课堂 | 接触前沿工具、完成更接近真实工作的复杂任务 | 首阶段主战场：Foundation → Agent 能力迁移 |
| 未来真实工作 | 在效率、质量、责任与协作约束下使用 Agent | 项目希望提前训练和研究的目标情境 |

## 十一、项目八重闭环

V2.2 要求项目同时满足以下闭环；任何一环长期无法成立，都应触发缩减范围、调整定位或停止扩张，而不是继续堆功能。

| **闭环** | **输入** | **输出 / 回流** |
|----|----|----|
| 问题闭环 | 课程更新较慢、Agent 工作方式变化快 | 定位为“教育基础—课余迁移—未来工作”的过渡层 |
| 用户闭环 | 学生想接触 Agent，但缺少结构化专业实践 | 可独立使用的学习路径、真实任务、即时反馈和可验证成果 |
| 产品闭环 | Foundation 基线 + Agent 任务 | 任务完成 → Verifier → 迁移任务 → 能力反馈 → 下一任务 |
| 研究闭环 | 规范取得的行为与结果数据 | 研究发现 → 任务设计/评价方式改进 → 新一轮数据 |
| 数据闭环 | Task-scoped Telemetry + 版本化环境 | Raw Event → 可重算指标 → 去标识化 Research Dataset |
| 采用闭环 | 个人自愿使用 / 第二课堂 | 学生复用 → 导师组织 → 学校支持 → 有条件进入课程拓展 |
| 工程闭环 | Spec / Task / Code | Implement → Test → Converge → Release → Pilot → 新 Issue |
| 竞赛闭环 | 产品、真实用户、原创数据、实证结论 | 可运行演示 + 应用证明 + 研究证据，避免只靠概念 |

## 十二、首阶段产品必须在“没有老师强制布置”的情况下也成立

首版学生端必须支持自主进入学习路径、选择双轨任务、获得 Managed Sandbox/Personal Node 执行环境、调用平台 Agent、完成 Verifier 与迁移任务、形成个人学习报告和可验证项目成果。教师/导师端用于组织班级、训练营、社团或第二课堂，但不能成为学生获得核心价值的必要前提。学校支持是扩展结果，不是产品成立条件。

## V2.2 首阶段落地原则

正式课堂是否允许 Agent 不再影响项目能否启动。首阶段优先面向学生课余自愿使用、AI/专业社团、创新训练、竞赛训练、就业技能拓展和教师自愿组织的第二课堂。平台先证明学生愿意持续使用、双轨任务确实能产生比“普通 AI 教程”更深的专业能力迁移，再寻求课程内融合。

## **项目要解决的核心矛盾**

传统实训主要依据最终结果判断学生是否完成任务。生成式智能体进入编程、数据分析、系统运维等数字技能学习后，学生可能借助智能体完成大量操作，使“任务做出来”与“学生真正掌握”之间出现新的偏差。单纯禁止人工智能既不符合现实趋势，也无法培养未来工作中的人机协同能力；单纯允许使用又可能使教师失去对真实能力的观察。SkillShift Lab 的目标是在两者之间建立可操作的教学机制。

# **1. 项目概述**

## **1.1 项目名称与定位**

项目名称：SkillShift Lab——AI时代职业数字技能双轨实训与能力迁移平台。首个应用与研究场景限定为高等职业教育专科“大数据技术（510205）”专业。

项目性质：以“学生自主课余实践 + 教师/学校可组织的第二课堂”为首阶段产品载体，以职业教育中的能力迁移为长期实证研究主线。SkillShift Lab 不要求正式课程立即开放 Agent，而是在既有基础教学与考试体系之外，先提供结构化的 Agent 职业实践；在规范治理下，用真实任务、真实操作和可验证结果研究学生如何把学校基础能力迁移为 Agent 时代的人机协同职业能力。

## **1.2 核心问题**

在数字技术类课程中，学生已能够利用具备代码、终端、文件和工具调用能力的智能体参与真实任务。传统评价通常只判断“最终任务是否完成”，但在智能体参与后，最终结果可能由学生、智能体或两者共同产生。由此出现两个新的教学问题：第一，教师难以区分“完成任务”与“真正掌握”；第二，学生未来需要的不仅是独立执行，还包括正确委托、判断、验证和接管智能体的能力。

## **1.4 首个试点范围**

- 专业：高职大数据技术（510205）。

- 产品首版：先做3个高质量双轨能力迁移单元与1个SQL/MySQL垂直切片；Gate通过后扩到6个任务，不追求大题库。

- 试点目标：先完成5–20名学生的课余/第二课堂小样本Pilot，并由至少1位专业教师/导师参与任务审核；是否进入正式课程由后续证据与学校审核决定。

- 研究初期：先完成产品、任务与测量机制验证，再进入正式Human研究；不以“全专业强制使用”或“课堂必须开放Agent”作为项目成立前提。

## **1.5 明确非目标**

- 不做全设备监控、摄像头监考、全键盘记录或浏览器历史采集。

- 不宣称平台能够证明学生没有使用手机、其他电脑或外部AI。

- 不按照“使用AI次数多少”直接判断能力高低。

- 不自研基础大模型，不把“接入某模型”作为创新点。

- 不做简单AI助教或聊天机器人；Agent协作只是实训流程的一部分。

- 不输出“某专业AI替代率”，也不直接决定课程删除或专业调整。

# **2. 立项背景与现实问题**

## **2.1 人工智能正在改变“完成技术任务”的方式**

职业教育中的编程、数据处理、数据库、平台运维等课程强调动手实践。随着生成式智能体具备代码生成、终端执行、配置修改和错误诊断能力，学生完成这些任务的路径正在发生变化。学生可以通过自然语言将部分步骤交给智能体，而教师传统的“看最终结果、看代码、看报告”方式越来越难完整判断学生在过程中承担了多少认知与决策工作。

OECD在2026年发布的职业教育与人工智能专题报告指出，人工智能正在同时影响技能需求、课程与资格体系的开发方式，并强调职业教育需要保持以人为中心、透明、可问责的数据与决策机制。\[1\] 对具体课堂而言，这种变化首先表现为：智能体已经进入学生实际完成任务的过程，而现有实训系统的评价机制未必同步改变。

## **2.2 “任务完成”与“学习发生”并不等价**

AI辅助可以显著提高任务完成表现，但任务表现提高不必然意味着概念理解或技能迁移同步提高。2026年一项编程教育随机实验发现，AI辅助组在练习任务得分上明显更高，但知识增益与代码理解并未出现同等幅度提升，提示“performance”与“learning”需要分开测量。\[4\] 因此，SkillShift Lab不把“作业成功率提高”直接解释为“学习效果提高”。

## **2.3 为什么不能把项目做成“AI检测/防作弊”**

现实中无法通过单一软件证明学生没有在手机、浏览器、其他电脑或同伴处获得外部帮助。将项目定位为“完整监控AI使用”会同时带来技术不可证、隐私风险与学生抵触。SkillShift Lab的评价范围限定为平台内可观察的人机协作过程，并通过设计更好的平台内Agent上下文、任务环境和验证工具，使学生有动力在平台内完成主要协作，而不是依靠强制监控建立可信度。

## **2.4 为什么选择高职大数据技术作为首个场景**

教育部2025版《大数据技术专业教学标准（高等职业教育专科）》覆盖数据采集、数据预处理、大数据分析、数据可视化、数据挖掘、大数据平台部署与运维等实践能力，并强调实践教学与真实职业场景。\[2\] 这些任务具有三个适合本项目的特征：一是可构造真实或近真实的软件环境；二是大量结果可以通过数据库、文件、服务状态和计算输出自动验证；三是学生使用智能体完成代码与系统操作已经具有现实可能。

## 2.5 正式教育与 Agent 行业演进存在时间差

项目不再把“Agent 将很快全面进入正式课堂”作为成立前提。对首个试点学校而言，课程、考试、考证和教学管理仍可能主要围绕基础知识与独立操作展开；同时，行业工具与学生个人实践已经快速进入 Agent 工作方式。SkillShift 将这种时间差视为真实约束，而不是要求学校先完成制度变革。

因此，首阶段落地优先选择课外实践、第二课堂、创新训练、技能拓展或教师自愿的小规模试点。正式课堂可以继续承担 Foundation Track，SkillShift 先补上从“学校基础技能”到“Agent 协同职业能力”的迁移层。

## 2.6 为什么“课余/第二课堂优先”比“先改正式课堂”更合理

OECD 2026 年职业教育专题报告指出，职业教育的课程和资格开发通常稳健但耗时，面对快速变化的数字化与 AI 技能需求存在更新速度压力；AI 在职业教育机构和教师层面的采用仍然不均衡、偏早期与探索性。\[1\] 这意味着“Agent 已改变部分工作方式”与“正式课堂马上同步改变”不能画等号。

教育部等五部门 2026 年《“人工智能+教育”行动计划》提出打造“短实新”的前沿创新课程，推动职业教育传统专业升级，并将人工智能纳入高校学生就业能力提升项目，鼓励微专业、微证书和面向师生开放的 AI 素养与技能资源。\[11\] 因此，本项目把课余/第二课堂作为首阶段入口，是项目根据现实采用速度作出的工程与教育策略，而不是把它包装成国家已规定的唯一教学模式。

本项目也不把“当前使用少”直接解释为“市场空白”。它只说明存在潜在采用缺口；是否构成真实需求，必须通过学生持续使用、教师/导师反馈和小规模 Pilot 证明。

# **3. 用户、场景与需求分析**

## **3.1 教师**

| **现实需求** | **当前痛点** | **SkillShift对应能力** |
|----|----|----|
| 发布真实技术作业/实训 | 普通LMS更适合文件提交和结果评分 | 任务模板 + Sandbox + Task Graph |
| 允许AI又不失去评价能力 | 最终正确无法说明学生真正掌握 | 过程事件 + Hidden Verifier + 能力报告 |
| 识别学生常见薄弱点 | 人工逐个阅读对话与终端过程成本高 | 班级聚合分析 + 错误类型统计 |
| 设计AI时代的新型任务 | 传统任务容易被Agent直接完成 | EDA-V任务结构 + 标准化错误场景 |

## **3.2 学生**

学生需要的是一个能真正帮助完成技术任务的统一工作台，而不是一个“监控器”。平台内Agent应理解当前任务、文件、环境状态和课程材料，减少学生反复复制错误日志和上下文的成本；同时通过“执行/修改/拒绝/先验证”等明确决策点，让学生逐步形成对智能体建议的判断能力。

## **3.3 专业与学校**

学校需要一套能够适应人工智能广泛进入学习过程的实训模式：既不回到“完全禁用”，也不把学习过程交给不可观察的外部工具。平台的价值在于提供可部署的课程试点、过程证据、结果验证和规范化数据治理，为后续教学调整提供证据而不是直接替代教师判断。

## **3.4 研究者与项目团队**

项目团队需要在不依赖企业私有数据的前提下获得高质量Human-Agent真实过程数据。产品真实使用能够形成“任务—Agent建议—学生判断—学生操作—Verifier结果—后续迁移表现”的纵向数据链，为职业教育中的人工智能使用研究提供比问卷或模型自评更直接的证据。

## 3.5 首阶段核心用户：学生自驱 + 导师组织，而非课程强制

首阶段的第一核心用户是已经具备一定计算机基础、希望在课余接触 Agent 真实工作方式的学生。产品必须让学生即使没有教师发布作业，也能沿“基础诊断 → Agent 协同任务 → 迁移任务 → 真实交付物 → 反馈与下一任务”的路径独立获得价值。

第二核心用户是教师、辅导员、社团指导老师、竞赛指导老师或训练营导师。他们不需要改变正式课程，只需从任务库选择路径、组建 Cohort、查看结果和组织复盘。学校/专业负责人是后续扩展用户，其价值来自学生参与、真实成果和研究证据，而不是被要求先批准全专业使用。

## **4.3 产品是否必须“全专业强制使用”**

不是。全专业统一使用可以成为未来应用成果，但不能成为项目成立条件。首版应先证明教师愿意使用、学生能完成任务、系统记录有价值、数据指标具有解释力，再从一门课扩展到多课程与专业级试点。若产品只能依靠行政强制才能产生价值，则说明产品价值本身不足。

## **4.4 产品价值与研究价值的边界**

| **场景** | **产品直接回答** | **研究进一步回答** |
|----|----|----|
| 一次作业 | 任务是否真正完成；学生如何与Agent协作 | 协作行为与基础能力/学习结果的关系 |
| 一个班级 | 哪些学生存在过度依赖、验证不足等现象 | 不同能力层次学生的Human-Agent差异 |
| 一门课程 | 任务/知识点上的班级能力分布 | 一学期后监督能力与迁移能力是否变化 |
| 长期 | 课程可持续使用与任务资产积累 | AI能力演进对职业技能培养方式的影响 |

## 4.5 双轨定位：Foundation Track + Agent Track

Foundation Track 用于确认学生在不依赖 Agent 或限制 AI 的条件下掌握了哪些基础知识、独立操作和核心原理；Agent Track 则允许或鼓励使用 Agent，但任务必须同步提高复杂度，重点观察委托、判断、验证、接管和真实结果。两条轨道不互相取代，而是形成“基础—迁移—协同”的连续路径。

双轨设计解决的是“课堂不一定允许 Agent”的现实限制：SkillShift 不要求原课程立即改成 Agent 课堂，而是能够在课外、实训拓展或后续进阶阶段，为同一技能提供 Agent 协同任务。

| **轨道** | **主要任务结构** | **AI政策** | **结果用途** |
|----|----|----|----|
| Foundation | 基础执行、概念与独立操作 | 无 Agent / 受限 AI | 课程基础确认、后续配对基线 |
| Agent | 更复杂、变化、诊断、验证、跨组件任务 | 允许/鼓励 Agent | 职业协同训练与过程数据 |
| Transfer | 等价新情境/迁移任务 | 按研究条件控制 | 区分当场Performance与真正Learning |

## 4.6 V2.2 的完整产品闭环

产品首页不再以“课程作业”为唯一入口，而同时提供“自主学习路径”和“导师/课程任务”。自主路径保证产品在没有制度强制时仍然有价值；导师/课程路径则让学校支持后能够自然扩展，而无需重写核心系统。

| **阶段** | **学生获得什么** | **系统产生什么** |
|----|----|----|
| Foundation Check | 确认自己是否理解该技能的基础概念与独立操作 | 基础任务结果、知识点/操作证据 |
| Agent Practice | 使用 Agent 完成更复杂、更真实的任务 | Agent 建议、学生决策、工具动作、环境状态 |
| Verifier | 知道“做出来”是否真的正确 | 机器可验证的 Evidence 与 Final Result |
| Transfer Task | 换数据、约束或故障，检验是否真正迁移 | 迁移表现与对原 Agent 路径的依赖程度 |
| Portfolio / Report | 形成可回看的项目成果与成长证据 | 版本化成果包、能力画像、后续建议 |
| Next Challenge | 继续更复杂任务，而不是无限刷简单题 | 难度校准、任务推荐和长期纵向数据 |

# **5. 产品总体流程与功能体系**

## **5.1 教师端流程**

1.  选择课程或创建课程。

2.  从任务模板库选择实训，或创建新Task Graph。

3.  配置实验环境、数据、Agent政策、是否使用Live Agent或Standardized Agent。

4.  定义Evidence Contract与Hidden Verifier。

5.  发布作业，设置时间、允许工具和提交条件。

6.  查看学生完成结果、协作轨迹摘要与能力画像。

7.  对任务质量、AI错误类型和班级共性问题进行复盘。

## **5.2 学生端流程**

8.  进入任务，阅读目标、限制条件与评价说明。

9.  在真实Terminal/Editor/数据环境中开始操作。

10. 需要时调用平台内Agent提出分析、方案或操作建议。

11. 对关键建议进行“执行/修改后执行/拒绝/先验证”等决策。

12. 通过系统提供的检查工具或自主方法验证中间状态。

13. 完成后触发最终Verifier并提交。

14. 查看面向学习的过程反馈与能力报告。

## **5.3 系统端流程**

| **创建隔离环境** | **→** | **加载任务状态** | **→** | **记录任务事件** | **→** | **运行Agent/学生操作** | **→** | **中间Evidence** | **→** | **最终Hidden Verifier** | **→** | **生成报告与提交** |
|----|----|----|----|----|----|----|----|----|----|----|----|----|

## **5.4 核心功能模块**

| **模块** | **首版能力** | **是否首版必须** |
|----|----|----|
| 课程与作业管理 | 课程、任务、截止时间、学生名单、发布/提交 | 是 |

| Sandbox | Terminal/Editor/数据/服务环境，重置与隔离 | 是 |
| Agent协作 | Live Agent + Standardized Agent 两种模式 | 是 |

| Hidden Verifier | 独立检查系统真实状态 | 是 |

## 5.5 多终端与三种执行形态

产品界面统一采用 Web/PWA，避免学校机房大量安装和版本维护。执行环境与界面解耦：任务在何处真正运行由 Execution Scheduler 根据任务要求、设备可用性和资源策略决定。学生看到的是同一工作区，不需要理解底层是自己的电脑、学校服务器还是远程 Sandbox。

远程控制自己的电脑可以在早期试点中使用，但正式产品更推荐“SkillShift Personal Node”：学生在自己的电脑安装轻量执行代理，通过出站安全通道向平台声明 CPU、内存、Docker/WSL、可用工具等能力，仅把指定任务工作区暴露给 SkillShift，而不是把整个桌面交给平台。没有个人电脑的学生始终可以选择 Managed Sandbox。

| **执行模式** | **典型入口** | **执行后端** | **核心价值** |
|----|----|----|----|
| Managed Remote Sandbox | 机房浏览器/任意浏览器 | 学校/云执行集群 | 零安装、覆盖无个人电脑学生、环境一致 |
| School/Lab Node | 机房浏览器 | 校内服务器或实验节点 | 低延迟、数据留校、可批量并发 |
| Personal Node | 浏览器/PWA + 本机Node | 学生自己的电脑 | 保留个人长期环境、课后持续学习、可远程连接 |

## 5.6 首版两种使用模式

| **模式** | **是否依赖教师** | **主要流程** | **首阶段优先级** |
|----|----|----|----|
| 自主学习模式 | 否 | 选择路径 → Foundation → Agent Task → Verify → Transfer → Portfolio | 最高 |
| Cohort / 第二课堂模式 | 需要导师组织但不改变正式课程 | 导师选任务 → 学生训练 → 班级/小组报告 → 复盘 | 高 |
| 正式课程融合 | 是 | 与课程、成绩、教务规则对接 | 后置，只有证据成熟后推进 |

为了提高课余持续使用率，每个任务必须产生明确的“可交付成果”，例如经过 Verifier 验证的代码、数据处理结果、环境快照摘要、故障诊断报告或小型项目。平台可以提供成长轨迹和作品集，但不得把未经外部认可的内部结果包装成职业资格证书。

# **6. 能力评价框架**

## **6.1 评价原则：结果与过程分开**

最终结果仍然重要：学生必须把任务真正完成。但只看结果不足以评价AI协同能力，因此平台将“Outcome”和“Process”分开。Outcome由Hidden Verifier与教师评价确定；Process通过任务内协作事件与关键决策点描述。

## **6.2 EDA-V：职业技能任务结构**

| **类型** | **定义** | **示例** | **主要观察** |
|----|----|----|----|
| E - Execute | 明确目标、正常环境中的标准执行 | 部署指定服务、完成数据处理 | 任务执行与Agent委托效率 |
| D - Diagnose | 环境已有隐藏故障，需要定位与修复 | 服务异常、数据链中断 | 状态检查、根因分析、接管能力 |
| A - Adapt | 条件发生变化，不能照搬旧路径 | Schema/版本/约束变化 | 迁移与调整能力 |
| V - Verify | 已有结果看似完成，需要判断真实正确性 | 发现配置/数据中的隐性错误 | 验证意识与专业判断 |

## **6.3 AI监督能力：不以“少用AI”为高分**

平台不把AI调用次数作为能力高低的直接指标。优秀学生可能大量使用Agent，但能够精确委托、识别错误、进行验证并在必要时接管；基础薄弱学生也可能使用次数很少，但只是在机械复制。因此，评价重点是“是否恰当地依赖AI（Appropriate Reliance）”，而不是“是否使用AI”。

| **指标** | **定义** | **注意事项** |
|----|----|----|
| 正确建议接受率 | 对确实正确且有帮助的Agent建议，学生合理采用的比例 | 不能鼓励无理由拒绝AI |
| 错误建议识别率 | 错误/不完整建议被拒绝、修改或通过验证发现的比例 | 核心监督指标 |
| 未验证执行率 | 高风险建议被直接执行且无前置验证的比例 | 仅对需要验证的建议统计 |
| 验证覆盖率 | 关键状态/高风险动作前后进行了有效验证的比例 | 需由任务定义“关键验证点” |
| 人工接管成功率 | Agent卡住或给错方案后，学生能否恢复任务 | 适用于D/A类任务 |
| 协作增益 | 使用Agent后相对独立条件在正确率/时间上的变化 | 属于研究指标，不宜作为个人单一分数 |

## **6.4 任务表现与学习效果分开**

平台内作业成功属于“任务表现”；真正的学习效果需要通过后测、等价迁移任务、延迟测验或限制AI的新任务评价。该区分是项目研究能否成立的核心。若只证明“使用Agent后作业做得更快”，不能据此推出“学生学得更好”。

# **7. 职业教育研究主线与研究问题**

## **7.1 长期研究主题**

研究主题统一为：生成式智能体进入职业技能实训后，学生的任务表现、学习效果、专业基础价值与人机协同能力发生了怎样的变化。研究的目标不是判断某项基础知识“是否应该取消”，而是通过真实数据识别哪些能力的作用位置发生了迁移。

## **7.2 核心研究问题（RQ）**

- RQ1：在同一职业技能中，Agent对Execute、Diagnose、Adapt、Verify四类任务的辅助效果是否存在系统差异？

- RQ2：Agent辅助提高的是短期任务完成表现，还是能够迁移到新的等价任务和延迟测验？

- RQ3：学生的专业基础水平是否影响其识别AI错误、验证结果和接管任务的能力？

- RQ4：Human+Agent相对于Human-only或Agent-only的优势主要出现在哪些任务结构和学生能力层次？

- RQ5：经过结构化的人机协同实训，学生的“适当依赖、验证与接管”能力能否在一个学期内提高？

- RQ6：课余/第二课堂的结构化 Agent 实训能否提高学生把课堂基础迁移到新任务、复杂任务和真实项目中的能力，并形成持续参与意愿？

## **7.3 待验证假设**

- H1：AI辅助可能显著提高短期任务完成率和效率，但学习增益不一定等比例提高。

- H2：专业基础较强的学生在Agent错误识别、验证覆盖和人工接管方面可能表现更好。

- H3：Execute类任务更容易被Agent直接辅助，而Diagnose/Adapt/Verify更能区分学生监督能力。

- H4：结构化的决策门、验证提示和错误场景训练可能提升学生的适当依赖能力。

以上均为研究假设，不是预设结论。若真实数据不支持，应修改研究解释，而不是调整数据或任务来维护项目叙事。

## **7.4 研究阶段**

| **阶段** | **主要对象** | **目标** | **是否产生教育结论** |
|----|----|----|----|
| R0 工程校准 | 任务、环境、Agent | 证明任务/Verifier/事件记录可稳定运行 | 否 |
| R1 教学Pilot | 1位教师、1个班、6任务 | 证明真实课堂可用，形成初步行为数据 | 仅描述性 |
| R2 对照研究 | Human / Human+Agent / 标准化错误条件 | 检验基础、监督能力、协同增益关系 | 是 |
| R3 纵向研究 | 一学期或多学期 | 观察监督能力、依赖与迁移能力变化 | 是 |

## 7.5 研究对象升级：从“课堂是否使用 Agent”转向“职业能力迁移”

长期研究主线调整为：在既有基础教学与考核体系不立即改变的条件下，学生如何把 Foundation Track 中形成的专业基础迁移为 Agent Track 中的真实人机协同职业能力；不同基础水平、任务结构和 Agent 条件如何影响这种迁移。

这使研究不依赖“学校必须允许 Agent 进入正式课堂”。正式课程成绩、基础轨任务和已有考核可以作为一种背景/基线；课外 Agent 轨与迁移任务用于观察学生面对未来工作方式时出现的新增能力、薄弱点与适当依赖行为。

## 7.6 第二课堂样本的研究边界

首阶段课余 Pilot 以自愿参加者为主，必然存在兴趣、能力和主动性上的自选择偏差。Pilot 首要用途是验证产品、任务和测量机制，而不是据此代表“所有高职学生”。只有后续进入更广泛班级、多层次样本并采用合适的对照与分层设计后，才讨论更广泛的教育结论。

因此，项目将“产品验证”和“正式因果研究”明确分开：前者允许小样本、迭代和可用性反馈；后者必须预先定义研究问题、纳排标准、条件、主要指标与分析计划。

# **8. 数据来源、实验设计与研究治理**

## **8.1 五类数据**

| **数据层** | **典型字段** | **用途** |
|----|----|----|
| 任务数据 | 技能单元、知识点、EDA-V类型、难度、环境版本 | 解释任务本身 |
| AI协作数据 | Prompt/建议类型、工具动作、建议正确性、学生处理方式 | 研究人机协作 |
| 学生操作数据 | 平台内命令、文件diff、检查动作、关键决策 | 研究真实执行过程 |
| 结果数据 | Verifier状态、提交物、教师评分、失败类型 | 判断真实任务结果 |
| 学习结果数据 | 前测/后测、迁移任务、延迟测验、限制AI任务 | 区分Performance与Learning |

## **8.2 教学数据与研究数据必须分开**

教学运行需要保存课程、学生、作业、成绩和提交记录；科研分析则应在学校规范、明确研究目的和必要授权条件下，将数据去标识化后进入独立Research Data Plane。学校要求学生使用平台提交作业，不等于学生自动同意其全部行为数据用于科研。

| **教学数据** | **→** | **最小筛选** | **→** | **去标识化** | **→** | **研究数据** | **→** | **统计分析** |
|----|----|----|----|----|----|----|----|----|

## **8.3 只采集任务必要事件**

平台采用Task-scoped Telemetry，不采集与当前课程任务无关的设备行为。首版应记录AI对话/建议、Agent工具动作、学生在平台中的接受/修改/拒绝/验证选择、任务Terminal命令、文件diff、Verifier事件、提交状态；不记录摄像头、全桌面、浏览器全部历史、私人聊天或无关应用操作。

## **8.4 外部AI使用的不可观测边界**

学生仍可能通过手机或其他工具获取帮助。SkillShift只能描述平台内可观察过程，不能证明“全部AI使用均被记录”。正式研究若要求控制外部工具，应通过实验条件、现场管理或专门测验设计实现，而不能用平台日志替代这一证明。

## **8.5 Human实验的最低原则**

- 先通过R0/R1验证任务稳定性，再开展大规模学生研究。

- 使用等价任务变体和随机/交叉设计，避免同一题记忆效应。

- 将参与者按课程阶段或基础水平分层，不把所有学生视为同一能力水平。

- 正式样本量依据Pilot效应量与统计功效分析确定，不预先拍脑袋固定。

- 研究用途遵循学校审批、知情说明、最小化采集与去标识化原则。

# **9. 任务体系与首个试点范围**

## **9.1 任务来源**

任务设计首先映射教育部专业教学标准与国家职业技能标准，再吸收课程实训、技能竞赛、教师真实教学任务和后续企业/实习案例。平台不允许由语言模型凭空生成“看起来像大数据”的任务后直接作为正式评价。

## **9.2 首版6个任务的选择原则**

- 结果可机器验证；

- 能够在隔离环境中复现；

- 覆盖数据、数据库、系统/平台等不同技能；

- 至少包含Execute/Diagnose/Adapt/Verify中的多个类型；

- 能制造“最终都做对，但人机协作质量不同”的场景；

- 环境成本可承受，适合课堂并发。

## **9.3 首版任务组合建议**

| **任务** | **领域** | **主要类型** | **核心训练点** |
|----|----|----|----|
| Linux服务故障定位与恢复 | 系统基础 | D/V | 检查状态、验证Agent根因判断 |
| MySQL数据导入与约束修复 | 数据库 | E/A | 标准执行、Schema变化适应 |
| SQL异常结果诊断 | 数据分析 | D/V | 识别“能运行但结果错”的查询 |
| 多源数据清洗与一致性校验 | 数据预处理 | A/V | 数据质量与隐性错误验证 |
| Hadoop节点配置与健康检查 | 平台运维 | E/D/V | 多节点状态与Evidence Contract |
| Kafka→Flink链路故障处理 | 实时计算 | D/A | 跨组件状态、错误建议接管 |

## 9.4 首阶段任务不是“AI 工具教程”，而是能力迁移单元

每个首发模块至少包含一个基础检查、一个 Agent 协同任务和一个迁移/验证任务。以 Python 爬虫为例，基础检查可以验证 HTTP、DOM 与数据解析；Agent 任务允许完整调用 Agent，但引入网页结构变化、异常数据、质量约束与真实交付；迁移任务更换站点或数据条件，检查学生是否只会重复 Agent 的旧路径。

任务成功的标准不是“用了更先进的模型”，而是：目标清楚、环境可复现、结果可验证、Agent 一句话不能完全消解学习目标、学生能产生可带走的成果。

# **10. 国内外相关产品与差异化定位**

## **10.1 现有产品已经覆盖的能力**

成熟虚拟实训平台已经能够提供真实/虚拟实验环境、AI导师、自动评分和基于环境状态的技能验证。Skillable公开资料显示其支持AI辅助实验开发、上下文导师、真实环境评分与多模型接入。\[6\]\[7\] Codio提供在线技术学习环境、自动代码评分等能力。\[8\] 因此，“虚拟实验室 + AI助教 + 自动判分”本身不能构成本项目的核心创新。

## **10.2 SkillShift的差异化**

| **比较维度** | **常见AI实训/学习平台** | **SkillShift Lab** |
|----|----|----|
| AI角色 | 帮助学习者完成任务 | 既是协作者，也是被学生判断与监督的对象 |
| 评价重点 | 知识/结果/操作是否正确 | 结果 + 学生如何接受、修改、拒绝、验证和接管Agent |
| 错误设计 | 尽量给正确帮助 | 可在Standardized Agent模式下加入受控错误/不完整建议 |
| 核心数据 | 学习行为与成绩 | Human-Agent关键协作事件 + 真实Verifier结果 + 迁移结果 |
| 科研问题 | AI如何帮助教学 | 学生需要什么专业基础才能正确使用和监督AI |

## **10.3 可主张与不可主张的创新**

| **可主张** | **不可主张** |
|----|----|
| 将“AI协作本身”作为职业技能训练与评价对象，而非仅作为教学辅助工具。 | “首个AI实训平台”或“首个自动评分平台”。 |
| 将Task Graph、Evidence Contract、Hidden Verifier与人机决策事件统一到同一作业闭环。 | “接入大模型就是技术创新”。 |
| 区分任务表现与学习效果，并用迁移/后测验证学生是否真正掌握。 | 仅凭平台日志证明学生没有使用任何外部AI。 |
| 通过真实教学持续产生Human-Agent职业技能协作数据。 | 在无数据情况下宣称某专业应减少基础学习或被AI替代。 |

## 10.4 与当前研究方向的关系

2026 年关于职业高等教育 AI 评价的研究指出，评价设计需要同时处理两类目标：一方面真实反映学生自身知识与能力，另一方面真实反映其在工作相关任务中使用合适 AI 工具的能力，并强调情境、协作/互动、过程与产出的职业真实性。\[12\] 这与 SkillShift 的 Foundation Track + Agent Track 并非完全同义，但为“双轨而非单一禁用/放任”提供了外部研究支撑。

同时，随机编程教育实验表明 AI 可以显著改善练习表现而不一定带来同等学习增益，\[4\]；适当依赖研究也显示，学生是否正确接受正确建议、拒绝错误建议，与单纯“信任 AI”并不是同一件事。\[5\] 因此，SkillShift 的核心评价必须继续坚持“Outcome、Process、Transfer 分开”，不能只做使用次数统计或最终成绩排行。

2026 年面向 ICT 与职业评价的多项框架也把“重新设计 Assessment”而非单纯 AI 检测作为重要方向。\[12\]\[13\] SkillShift 的差异化不在于提出这一宏观问题，而在于把它落到可执行技术任务、Agent 行为、隐藏验证和纵向能力迁移数据。

# **11. 竞赛适配与评审价值**

## **11.1 建议参赛形态**

若产品达到稳定演示、真实课余/第二课堂用户试点与可复核实证数据水平，建议以“可运行科技产品 + 原创任务/数据 + 实证研究结果”为主体组织参赛材料；若后续进一步获得正式课程试点则作为更强应用证据，而不是前置条件。产品提供应用价值与展示性，研究提供科学性与原创数据。最终类别与申报要求仍以届时正式赛事规程为准。

## **11.2 评审关注点映射**

| **评审关注** | **项目支撑** |
|----|----|
| 问题真实性 | 学生已在技术作业中使用Agent，传统结果评价难以反映真实掌握。 |
| 科学性 | 任务可复现、Verifier客观、Human/Agent条件可控、区分Performance与Learning。 |
| 先进性 | 研究对象从“AI帮助学生”推进到“学生如何监督AI”，关注appropriate reliance。 |
| 现实意义 | 为教师提供允许AI条件下的实训组织与评价工具，为学校提供试点证据。 |
| 完成度 | 可现场发布任务、运行Sandbox、调用Agent、验证结果、提交并生成报告。 |
| 自主数据 | 真实课程中的Human-Agent协作轨迹与迁移任务数据。 |

## **11.3 五分钟现场演示建议**

最有辨识度的演示不是聊天，而是“两个学生最终都PASS，但协作能力不同”的情境。现场选择一个带隐藏错误的任务，Standardized Agent给出一条表面合理但实际错误的建议；演示者直接接受后，系统记录未验证执行和风险。随后展示另一条通过检查、拒绝错误建议并正确接管的轨迹。最终两人任务结果可能相同，但过程画像明显不同。

## **11.4 评委可能质疑与回答边界**

| **质疑** | **回答原则** |
|----|----|
| “这不就是AI助教吗？” | 核心不是让AI更会教，而是训练和评价学生是否会正确使用、判断和接管AI。 |
| “学生用手机问AI怎么办？” | 平台不宣称监控全部外部行为；研究需要控制条件时用实验管理解决。 |
| “AI会做了，为什么还要学基础？” | 项目正是要用迁移任务和错误识别实验检验基础的监督价值，不预设取消基础。 |
| “已有Skillable/Codio。” | 现有平台重点是AI辅助与技能验证；本项目把AI协作决策和监督能力作为评价对象。 |
| “一个高职学生凭什么研究职业教育？” | 项目从本专业真实课堂与实训切入，只回答可由真实数据验证的局部问题，不替全国职业教育下宏观结论。 |

# **12. 可行性分析与学校试点路径**

## **12.1 技术可行性**

首个专业中的数据库、数据处理、Linux和部分大数据组件可以在Docker、WSL2或虚拟机中构建可复现环境；任务结果可通过SQL查询、文件hash、服务状态、数据输出与集群健康检查进行客观验证。产品不需要自研基础模型，只需要通过统一Agent Adapter连接可用的商业或开放Agent。

## **12.2 组织可行性**

首版不要求老师改变正式课堂规则，也不要求学校全专业统一部署。更可行的组织路径是：先由项目团队面向自愿学生开展课余/第二课堂 Pilot，邀请 1 位或多位专业教师以“任务顾问/导师”身份审核任务，不要求其改变现有教学；只有学生持续使用、任务有价值且系统稳定后，再尝试由老师组织 Cohort、社团训练或课程拓展。

## **12.3 数据可行性**

项目的大部分任务、环境、Verifier和运行数据可以由团队自行构建。学生数据需要在真实试点后产生，因此R0开发不能把“已有大规模学生数据”当作前提。数据规模应随着教学应用自然增长。

## **12.4 模型与Agent选择**

产品不自研模型，采用Model-Agnostic架构。教学中的Live Agent优先接入学生和教师真实可能使用的主流Agent；科研公平比较时可增加统一Harness或Standardized Agent轨迹。开放Agent用于可复现基线，但不承担“代表现实用户”的唯一角色。

| **模式** | **用途** | **优势** | **限制** |
|----|----|----|----|
| Live Agent | 真实教学协作 | 贴近真实使用、上下文动态 | 模型升级导致条件变化、API成本 |
| Standardized Agent | 公平训练/测评 | 所有学生遇到相同建议，可注入受控错误 | 不完全代表实时最强Agent |
| 开放Agent基线 | 研发与复现 | 版本可留存、便于方法验证 | 现实使用代表性可能较低 |

## **12.5 从个人课余使用到学校支持的扩展路径**

| **6任务内部Demo** | **→** | **1位教师评审** | **→** | **1个班Pilot** | **→** | **1门完整课程** | **→** | **多班级复现** | **→** | **专业级试点** |
|----|----|----|----|----|----|----|----|----|----|----|

扩展顺序冻结为“个人自愿使用 → 小型课余 Pilot → 导师/社团/训练营 Cohort → 第二课堂或专业拓展项目 → 有条件的正式课程融合”。学校支持应建立在学生使用证据、教师任务审核和真实成果之上；全专业统一使用仍然只是远期应用成果，不是项目成立条件。

## 12.6 机房、个人电脑与“无电脑学生”的现实约束

首版必须把“学校机房电脑不能随意安装软件”“学生个人电脑配置差异大”“部分学生没有个人电脑”作为一级产品约束。任何核心功能都不能只在高配置个人电脑上成立。

最低兼容原则为：机房浏览器可完成全部核心流程；无个人电脑学生可以使用 Managed Sandbox；有个人电脑学生可安装 Personal Node 获得本地长期环境；教师和后台均通过 Web 管理。任务通过 Capability Manifest 声明所需资源与组件，调度器只把任务派发到满足条件的执行后端。

| **约束** | **产品对策** |
|----|----|
| 机房无管理员权限/不允许装复杂软件 | Web/PWA 作为默认入口，执行环境放在校内/远程节点 |
| 学生电脑配置不一致 | Personal Node 上报能力；Task Capability Manifest + Scheduler匹配 |
| 学生无个人电脑 | Managed Sandbox 保证核心功能不依赖个人设备 |
| 远程连接/NAT/防火墙 | Personal Node 使用客户端主动建立出站加密连接，不要求公网入站端口 |
| 本地隐私与安全 | 只开放指定workspace/任务能力，默认不采集完整桌面和个人目录 |

## 12.7 课余产品必须解决“为什么学生愿意持续回来”

第二课堂没有考试和学分的天然强制力，因此留存本身就是产品有效性的证据之一。SkillShift 不依赖签到或刷时长维持活跃，而通过三种价值让学生愿意继续：①真实使用主流 Agent 做更复杂项目；②每次训练都有机器可验证的成果与作品包；③任务难度逐步提升并明确展示从基础技能到 Agent 职业能力的成长。若学生只能获得“看教程 + 聊天 + 徽章”，则项目应视为偏离核心。

## 13.1 V2.2 的 P0 证据验证路线

在 M1/MVP 正式开发前，先完成四步 P0。其目的不是继续讨论项目，而是用真实旧题、教师和少量学生验证项目的两个关键假设：①传统数字技能任务是否真的因 Agent 出现而失去部分评价能力；②双轨任务和过程数据是否为教师/学生带来比原方式更多的信息。

|----|----|----|
| P0-A | 10–20道真实旧实训 → 主流Agent冲击审计 | Agent可直接完成程度、失败类型、用时、人工介入；禁止解读为专业替代率 |
| P0-B | 3–5位教师半结构化访谈 | 至少1位愿意提供真实任务并参与重构；否则重新评估需求 |

## 13.2 V2.2 阶段门：先验证“学生自驱产品”，再验证“学校采用”

| **阶段** | **核心工作** | **通过条件（Go 信号）** | **失败时怎么做** |

| P0-A 任务冲击审计 | 10–20 道真实旧实训让现实 Agent 运行 | 能识别哪些旧任务被显著压缩、哪些仍有区分力；保留失败案例 | 若大多数任务并未被 Agent 显著改变，则收缩问题定义 |

# **17. 工程目标与设计原则**

工程目标不是快速堆出一个“AI教育网站”，而是构建一个学生可自主使用、导师可组织、能够在真实或近真实技术环境中运行、记录必要 Human-Agent 事件并客观验证结果的最小平台。首版工程优先服务课余能力迁移闭环、产品可用性与研究可解释性，正式教务系统对接后置。

- 真实任务优先：所有核心功能围绕可以实际执行的职业技能任务。

- 结果确定性优先：能够由程序验证的结果，不交给LLM主观打分。

- 人类决策显式化：关键Agent建议需要形成可记录的学生决策点。

- 最小监测：仅记录任务范围内必要事件。

- 教学/科研解耦：Operational Data与Research Data逻辑分离。

- 模型无关：Agent通过Adapter接入，不绑定单一供应商。

- 任务版本化：任务、环境、Verifier、Agent策略和事件Schema必须显式版本。

- 产品可用优先：首版不追求大规模功能，6个任务端到端完成度优于100个半成品题目。

## 18.2 V2.2 宏观架构：控制面、执行面、评价面与数据面

完整系统采用“界面统一、执行解耦”的架构。学生、教师、管理员使用统一 Web 应用体系；真正运行任务的资源可以位于学校、云端或学生自己的电脑。所有后端都通过统一 Execution Adapter 与 Session Orchestrator 对接。

| **层/面** | **关键组件** | **职责** |
|----|----|----|
| Client Layer | Student Web/PWA、Teacher Web、Admin Console | 角色化交互；不把执行环境与界面绑死 |
| Control Plane | API Gateway、Auth/RBAC、Course/Assignment、Task Engine、Session Orchestrator、Scheduler | 任务、权限、会话、执行后端调度和全局状态 |
| Agent Plane | Agent Gateway、Model/Provider Adapter、Policy、Quota、Standardized Trace | 统一Agent接入、上下文、配额、版本和安全策略；API Key不下发学生端 |
| Execution Plane | Managed Sandbox、School Node、Personal Node、Terminal/Editor/Data Runtime | 执行代码/命令/服务；声明能力并接受任务Session |
| Evaluation Plane | Evidence Collector、Hidden Verifier、Report Engine | 独立验证真实状态，避免由Agent自评 |
| Data Plane | Operational DB、Event Store、Artifact Store、Research Export | 教学运行与科研导出分离，支持版本和审计 |

## 18.3 客户端与后台控制台边界

学生端、教师端和后台控制台不是三个独立系统，而是共享同一后端与权限模型的三个角色化入口。首版可以在一个 Web 前端项目中按路由/角色拆分，后续再按规模拆服务。Personal Node 是执行代理，不是第四套完整UI。

| **入口** | **首版核心页面** |
|----|----|
| Student | 任务列表、Foundation/Agent轨、Workspace、Agent、Evidence/Checkpoint、Submit、个人反馈 |
| Teacher | 课程/班级、任务模板、双轨配对任务、发布、Session摘要、个人/班级报告、任务复盘 |
| Admin/Ops | 用户与角色、执行节点、资源配额、Agent Provider/Key、任务/环境/Verifier版本、队列、健康、审计 |
| Research（后续） | 研究Condition、去标识化数据版本、导出、分析任务；不访问教学身份 |

## 18.4 统一执行接口与 Capability Manifest

每个 TaskVersion 声明 Capability Manifest，例如操作系统、CPU/内存、Docker/WSL、数据库/服务、网络策略、磁盘、GUI需求。每个 Execution Node 周期性上报自身能力与负载。Scheduler 只把任务派发到满足要求的节点，使同一任务既能跑在学校服务器，也能跑在个人电脑或远程Sandbox。

ExecutionAdapter 最低接口建议：describe_capabilities()、prepare_session()、exec_command()、read/write_workspace()、stream_terminal()、snapshot()、freeze_for_verify()、reset()、destroy()。对 Personal Node 额外要求用户显式绑定设备、workspace白名单和可撤销授权。

## 19.3 首版角色优先级

P0/M1 优先级固定为：学生端 \> 最小后台运维 \> 导师/教师端 \> 正式研究者端。学生必须能在无老师建课的情况下进入公开/授权学习路径；后台只保证账号、节点、任务、Agent 与资源可用；导师端首先提供 Cohort、任务分配和报告，不建设复杂教务功能。

# **20. Task Engine：Task Graph 与 Evidence Contract**

## **20.1 Task Graph**

Task Graph用于把一项真实实训拆成可管理的目标阶段，而不是强制学生按固定步骤操作。节点可以表示“理解目标、检查状态、执行修复、验证结果、提交”等阶段；边表示允许的前后关系或解锁条件。对于开放任务，Task Graph只定义必要里程碑，不限制学生必须采用某条唯一操作路径。

## **20.2 Evidence Contract**

Evidence Contract定义“什么证据足以说明某个阶段或最终任务完成”。证据应尽量来自真实系统状态。例如数据库恢复任务可以要求服务可用、目标表存在、指定数据一致、时间点满足条件；不能以学生或Agent文本声明作为最终证据。

# **21. Sandbox 与真实实训环境**

## **21.1 环境策略**

首版根据任务复杂度混合使用Docker/Compose、WSL2或虚拟机。数据库、Python数据处理和轻量服务优先容器化；需要systemd、多节点网络或复杂平台状态的任务再使用VM/WSL2。统一要求是可创建、可重置、可检查、可销毁。

## **21.2 生命周期**

| **建立环境** | **→** | **健康检查** | **→** | **注入任务** | **→** | **人机协作** | **→** | **冻结状态** | **→** | **隐藏验证** | **→** | **归档/重置** |
|----|----|----|----|----|----|----|----|----|----|----|----|----|

## **21.3 隔离要求**

- 不挂载宿主机私人目录和真实凭据。

- Verifier、参考答案与故障Ground Truth不可被学生或Agent读取。

- 高风险命令在一次性Sandbox中运行；必要时设置权限白名单。

- 不同学生Session之间不可共享可变状态。

- 环境镜像或快照使用明确版本/哈希，不使用不可追踪的latest。

## 21.4 SkillShift Personal Node：学生自己的电脑如何进入系统

Personal Node 是安装在学生个人电脑上的轻量执行代理，主要解决“希望软件长期伴随个人学习、但学校机房又不能依赖每个人都有电脑”的矛盾。它不承担课程UI，学生仍从Web/PWA进入；Node只负责在经过授权的任务工作区中提供Terminal、文件、Docker/WSL/本地工具等执行能力。

网络采用Node主动连接服务器的出站长连接/安全隧道，避免要求学生配置公网IP和入站端口。服务器只给已绑定设备分发签名Session与最小权限命令。Node不应默认提供全桌面远控，不读取与任务无关的目录和个人应用。

- 有个人电脑：可把自己的环境作为长期学习节点，课后继续训练，并保留个人工具链。

- 没有个人电脑：使用 Managed Sandbox，学习功能不降级到“只能看不能做”。

- 机房电脑：仅使用浏览器即可；若学校允许，可后续安装 School Node，但不是首版前提。

- 通用远程桌面：仅作为早期调试/应急手段，不能承担正式过程数据与评价依据。

## 21.5 Managed Sandbox：无个人电脑学生的兜底能力

Managed Sandbox 是产品公平可用性的底线。所有核心基础轨/Agent轨任务至少应提供一种项目方可控的远程执行形态。资源较重的大数据任务可以采用预约/队列/限并发，而不能要求学生必须购买高配置电脑。首版优先覆盖SQL、Python、Linux、数据处理等轻中量环境，Hadoop/Kafka/Flink等较重任务在资源条件验证后逐步开放。

# **22. Agent Integration：Live Agent 与 Standardized Agent**

## **22.1 Live Agent Mode**

Live Agent连接现实可用的主流Agent API/SDK/CLI。它拥有当前任务说明、允许的课程资料、工作区文件和必要环境状态，可以给出分析、代码、命令或工具动作。Live模式用于真实教学体验和生态适配。

## **22.2 Standardized Agent Mode**

Standardized Agent使用预先冻结的真实Agent轨迹或经专家审核的建议脚本，使所有学生面对相同的正确、错误、不完整和不确定建议。它主要用于公平评价“学生是否能判断AI”，并降低API版本变化与成本对实验的影响。

## **22.4 重要工程原则**

Agent输出不能直接写入“正确/错误”标签。建议正确性需要由任务Ground Truth、Verifier或专家标注确定。Live Agent可能在同一任务的不同运行中产生不同建议，因此需要记录模型、Harness、版本、工具、系统提示与时间。

## 22.5 Agent Gateway 与密钥/网络策略

学生端和 Personal Node 不保存平台商业 Agent 的主 API Key。Agent Gateway 在服务端统一完成Provider适配、模型选择、用量、预算、速率限制和审计；客户端只获得Session级短期令牌。若学校网络无法直接访问某供应商，可通过可用的合规Provider、校内代理或Standardized Agent运行，不把单一境外API可用性作为产品成立条件。

# **23. Human-in-the-loop 决策与协作事件**

## **23.1 决策门**

对可能改变任务状态的重要Agent动作，平台应提供可记录的学生决策。最小动作包括：Accept/Execute、Modify then Execute、Reject、Verify First、Take Over。低风险纯解释类消息不必强制决策门，避免把产品做成繁琐审批系统。

## **23.2 事件模型**

| **事件** | **关键字段** | **用途** |
|----|----|----|
| agent_suggestion | suggestion_id, type, content_hash, risk_level | 记录Agent提出什么 |
| human_decision | suggestion_id, decision, rationale_optional | 记录学生如何处理 |
| tool_action | actor, tool, command/action, result | 记录真实操作 |
| verification | target, method, result | 记录是否主动验证 |
| takeover | reason, start/end, outcome | 记录Agent失败后的人工接管 |
| evidence | contract_id, evidence_type, result | Task Graph节点证据 |
| final_verification | verifier_version, checks, pass/fail | 最终真实结果 |

## **23.3 不采集的事件**

不记录与任务无关的键盘输入、桌面活动、摄像头、麦克风或个人浏览行为；平台也不尝试在系统级阻断学生使用其他软件。首版只对平台内真实任务工作区负责。

# **24. Hidden Verifier 与结果可信判定**

## **24.1 原则**

- Verifier在学生和Agent权限边界之外执行。

- 优先检查最终真实状态，而非自然语言解释。

- 每个Verifier同时输出pass/fail和可审计的check明细。

- Reference Solution必须稳定通过，负例必须稳定失败。

- Verifier版本变化必须显式升级，旧Run永久关联旧版本。

# **25. 作业提交、评分与能力报告**

## **25.1 提交对象**

提交不是单一ZIP文件，而是一个Submission Package：最终环境状态摘要、指定文件/代码、Evidence结果、Verifier报告、学生必要说明和任务内协作摘要。教师仍可进行人工批注与课程成绩评定。

## **25.2 能力报告原则**

首版报告采用多维画像，不给未经验证的“AI监督总分”。报告分为结果层、技能层和协作层：结果层说明任务是否完成；技能层按EDA-V/知识点汇总；协作层展示正确建议处理、错误建议识别、验证行为与接管情况。

## **25.3 学生与教师看到的内容不同**

| **对象** | **主要展示** |
|----|----|
| 学生 | 任务结果、关键错误、建议反思点、验证覆盖、AI协作行为提示 |
| 教师 | 个人完整摘要、班级分布、常见Agent误用、常见知识/技能薄弱点、任务质量反馈 |
| 研究者 | 去标识化事件、实验条件、任务版本、结果，不包含直接身份字段 |

## 25.4 Verified Portfolio：课余学习的成果闭环

课余学习缺少正式成绩约束，因此每个模块应输出一个可复核成果包：任务版本、最终交付物、Verifier 摘要、关键 Evidence、必要的学生反思/说明和迁移任务结果。学生可以把它作为个人项目复盘或作品展示材料，但平台不得把内部评分包装成国家职业资格、行业认证或就业承诺。

# **27. 教学数据与科研数据双平面**

## **27.1 Operational Data Plane**

保存教学必须信息：账号、课程、班级、作业、Session、提交、成绩、教师批注。访问权限按课程和角色控制。

## **27.2 Research Data Plane**

科研数据由Operational数据经过目的检查、字段最小化、去标识化/伪匿名处理后生成。Research Participant ID与学号/姓名的映射应隔离存放并严格限制访问。正式研究数据导出必须记录数据版本、纳入/排除规则和授权状态。

## **27.3 数据保留与删除策略**

首版需明确不同数据的保留周期：教学提交按学校课程需要保存；高粒度操作事件不应无限期保存；研究数据按研究协议管理。系统应提供按课程/参与者删除或匿名化的能力，并保留必要审计记录。具体期限在学校试点前与指导教师和管理要求共同确定。

# **28. Research Module 与实验接口**

## **28.1 实验条件**

系统需要为后续研究预留Condition概念，例如Human-only、Human+Live-Agent、Human+Standardized-Agent、限制AI等；但首版教学产品不必把每节课都变成实验。只有经过教师与研究方案批准的Session才进入正式研究条件。

## **28.2 等价任务变体**

研究时同一技能应设计A/B/C等价变体，避免参与者先完成某题再在另一条件重复同一道题。变体应保持技能目标和难度接近，只改变数据、参数、故障位置或上下文。

## **28.3 后测与迁移任务**

为了回答“有没有学会”，Research Module需要支持与原作业不同但能力等价的迁移任务，并允许配置无AI/限制AI条件。只有这样才能把“当场完成”与“形成可迁移能力”区分开。

|----|----|
| 账号与权限 | RBAC；教师只能访问所属课程；研究者不直接访问教学身份数据 |
| Sandbox | 默认不访问宿主私人目录、真实密钥和校内敏感系统 |
| Agent数据 | 发送给第三方Agent的上下文最小化；明确哪些课程数据可外发 |
| 日志 | 不记录无关个人活动；敏感字段脱敏；Raw event访问受限 |
| 研究 | 明确研究目的、授权/同意、去标识化、可撤回/删除机制按学校要求实施 |
| 外部模型 | 记录供应商、版本与数据政策；涉及学生个人信息时不得默认直接发送 |

# **31. 测试、可观测性与可复现性**

## **31.1 必须自动化测试的对象**

- Task schema validation。

- Environment build/restore与health check。

- Reference Solution回归。

- Evidence Contract与Hidden Verifier正负例测试。

- Agent Adapter接口与异常退出。

- Telemetry事件完整性与顺序。

- Submission Package生成。

- 报告指标从Raw Event可重算。

- 教学/研究数据隔离与权限测试。

## **31.2 可观测性**

平台需要区分“学生失败、Agent失败、任务错误、Sandbox故障、Verifier故障、系统服务故障”。如果基础设施错误被当成学生能力数据，会直接污染研究结论。因此所有Session都应有基础设施健康状态和错误分类。

## **31.3 可复现性**

正式研究Run需记录TaskVersion、EnvironmentVersion、VerifierVersion、AgentSystemVersion、TelemetrySchemaVersion、实验Condition和必要随机种子；统计图表应能从版本化Research Dataset通过脚本重新生成。

**第三部分**

开发治理与 Agent 原生工作流

# 35. 为什么 SkillShift 需要 Dev OS

SkillShift 由个人主导、长期迭代并大量使用 Codex、Claude 等 Agent。最大的工程风险不只是代码错误，而是“项目状态漂移”：聊天、计划书、README、代码和 Agent 记忆各自形成不同版本。V2.2 将开发治理正式纳入项目路线，目标是降低认知负担，使任何功能都能从问题、规格、实现、验证追溯到发布。

## 35.1 核心原则

- 计划书保存长期路线与研究知识，不承担日常任务状态。

- Git 仓库中的 PROJECT_BRIEF / 架构 / ADR / Feature Spec 承担可执行开发上下文。

- GitHub Issues / Project 承担当前工作状态；Git 承担代码历史；CI/Test 承担是否真正可用的机器证据。

- 一个 Agent 一次只负责一个边界清晰、可验证的 Task；重要并行任务使用独立 Branch / Worktree。

- 重要 Feature 必须有 Acceptance Criteria；“Agent 说完成了”不等于 Done。

# 36. Source of Truth 分层

| **层级** | **权威内容** | **不应该存什么** |
|----|----|----|
| 项目计划书 V2.x | 为什么做、长期产品/研究路线、重大边界 | 每天的任务状态、临时代码细节 |
| PROJECT_BRIEF.md | 开发 Agent 每次必须知道的稳定事实 | 几十页背景材料 |
| AGENTS.md | Agent 操作规则、禁止事项、完成标准 | 业务需求细节 |
| Architecture + ADR | 当前架构与“为什么这样设计” | 任务进度 |
| Spec Kit Feature Artifacts | 单个功能的 what/why、plan、tasks、convergence | 全项目战略 |
| GitHub Project / Issues | 当前待办、依赖、状态、阻塞 | 完整需求正文的重复副本 |
| Git / PR | 实际代码变化和审阅证据 | 产品路线 |
| CI / Tests / Runtime Evidence | 功能是否可构建、测试和运行 | 主观“看起来没问题” |
| Release | 当前正式可用版本 | 尚未验证的实验实现 |

# 37. Feature、Bug、Research 的闭环

GitHub Spec Kit 当前官方流程以“Specify → Plan → Tasks → Implement → Converge”为核心，对生产级功能可加入 Clarify、Checklist 与 Analyze 质量闸门；Converge 会重新对照 spec/plan/tasks 检查代码并追加遗漏任务。\[16\] SkillShift 采用这一思路，但按工作类型裁剪，避免流程本身比开发还重。

| **工作类型** | **入口** | **推荐闭环** |
|----|----|----|
| FEATURE | 真实需求 / P0证据 / 已批准想法 | Assess → Specify → Clarify → Plan → Tasks → Implement → Test → Converge → PR → Release |
| BUG | 可复现异常 | Reproduce → Root Cause → Scoped Fix → Regression Test → Verify → PR |
| RESEARCH | 明确研究问题 | Question → Protocol → Evidence → Analysis → Limitation → Decision → 产品/研究下一步 |
| REFACTOR | 已识别技术债 | 理由/边界 → 测试保护 → 小步修改 → 回归验证 |
| DOC | 知识资产变化 | Scope → 更新唯一权威文档 → 一致性检查 → 合并 |

# 38. 多 Agent 隔离、Evidence 与 Definition of Done

并行 Agent 默认遵循“一 Issue = 一 Branch = 一 Worktree”。除非明确为只读研究，不让多个 Agent 同时写同一工作目录；冲突由人类项目负责人决定。每个任务结束必须提交 Files Changed、Why、Test Commands、Test Results、Acceptance Criteria PASS/FAIL、Known Limitations、New Risks 与 Git Diff Summary。

Feature 的 Done 条件统一为：Spec 满足 + Acceptance Criteria 通过 + 测试/构建通过 + Converge 无关键缺口 + 必要文档更新 + PR 合并 + 可运行 Demo/Runtime Verification。只有代码写完但没有验证，一律保持 Verify 状态。

# 39. V2.2 精确下一步

| **顺序** | **动作** | **产物** | **是否允许并行业务开发** |
|----|----|----|----|
| 1 | 只读审计现有项目与仓库状态 | DEV_OS_AUDIT.md | 否 |
| 2 | 建立最小 Dev OS：AGENTS / PROJECT_BRIEF / ADR / Issue / PR / CI | 可运行开发治理骨架 | 仅允许小范围 |
| 3 | P0-A：收集 10–20 道真实旧实训并做 Agent 冲击审计 | P0-A 报告 + 原始 Run | 是，只读/实验类 |
| 4 | P0-B：学生需求 + 教师/导师访谈 | 需求证据与反例 | 否，不扩大平台 |
| 5 | P0-C：重构 3 个双轨能力迁移单元 | Task Spec + Reference + Verifier | 允许单任务基础设施 |
| 6 | M1：SQL/MySQL Vertical Slice | 学生自主端到端闭环 | 是，严格按 Spec |
| 7 | P0-E：5–20 人课余 Pilot | 留存、可用性、过程/迁移数据 | 根据 Gate 决定 |
| 8 | 6 任务 MVP / Cohort / Research Pilot | 产品+应用+研究证据 | 通过 Gate 后进入 |

开发决策原则：在前一 Gate 没有证据通过时，不用“Agent 开发很快”作为提前建设下一层系统的理由。SkillShift 的工程效率优势应该用于更快验证假设，而不是更快制造未被需要的功能。

| 大模型是不是自己训练？ | 不是。通过Adapter接入主流Agent；模型是协作对象而非项目本体。 |
| 核心技术是什么？ | Task Engine、Sandbox、Agent Gateway、决策事件、Evidence Contract、Hidden Verifier、双平面数据。 |
| 最大风险是什么？ | 指标效度、学校试点、隐私治理、与成熟实训平台的差异化。 |
