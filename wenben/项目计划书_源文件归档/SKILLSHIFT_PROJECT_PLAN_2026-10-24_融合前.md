# SkillShift 项目总体计划书

**项目名称：** SkillShift Lab  
**计划日期：** 2026年10月24日  
**适用阶段：** R0/R0.5 项目基线与研究最小闭环准备  
**文件用途：** 说明项目目标、当前范围、推进阶段和判断依据，供项目负责人审定

## 项目摘要

SkillShift 研究 Agent 参与职业数字任务后，学习者的基础能力、协作过程和迁移表现之间有什么关系。项目关注学生能否理解任务、判断 Agent 建议、检查结果、修正错误，并在条件变化时继续完成相关工作。

SkillShift Studio 是开展这项研究的工具环境。它帮助教师组织任务，帮助学生完成任务，并把必要的任务证据交给教师复核。Studio 本身不是研究结论，也不是项目的全部。

项目当前处于合成原型和研究准备阶段。近期先整理可核对的项目基线，再确定一个职业任务族，形成可复现的任务和研究方案。真实课堂、学习效果、真实模型、学生代码执行和生产部署均未作为当前成果，也不由本计划书自动授权。

## 一 项目要解决的问题

学生在 Agent 帮助下完成任务，不等于学生已经掌握相关技能。最终产物只能说明结果是否符合要求，不能单独说明学生是否理解过程、发现错误或能在新情境中继续完成任务。

教师需要知道任务结果如何产生、哪些关键判断由学生完成、哪些结果经过验证。学生也需要在使用 Agent 时保留理解、检查、纠错和承担结果的能力。

SkillShift 因此关注三个相连的问题：学生已有的基础能力如何；学生在 Agent 协作中怎样理解、验证、纠错和接管；这些过程能否帮助解释学生面对变化任务时的迁移表现。

## 二 项目目标

### 近期目标

1. 建立项目文件、代码、规格和测试证据的可核对基线，区分当前状态、历史记录、计划事项和未知事项。
2. 从候选任务中确定一个职业数字任务族，形成任务来源、目标、参考解、正反例、可检查规则和迁移变体。
3. 设计一套可被推翻的研究方案，说明比较对象、证据、分析方法和结论限制。
4. 只保留支持上述任务和教师复核所需的最小 Studio 原型能力。
5. 在获得适当授权后，邀请教师或领域人员检查任务是否清楚、证据是否有用、复核负担是否合理。

### 长期目标

在多个任务和受控研究中，逐步判断基础能力与人机协作、迁移表现之间的关系，形成可复核的任务设计方法、研究证据和适用边界。只有证据支持时，才考虑扩展到更多任务、真实模型或真实使用场景。

## 三 项目是什么

SkillShift Lab 是一个以职业任务为基础的研究项目，研究 Agent 参与后职业技能训练和评价需要怎样调整。

SkillShift Studio 是项目的研究基础设施，提供教师任务配置、学生任务实践、必要过程证据和教师复核入口。Studio 不负责自动判断学生是否作弊，不自动给出能力结论，也不以和主流 Agent 竞争为目标。

项目的研究关系可以这样理解：

```text
基础能力
   ↓
学生与 Agent 完成职业任务
   ↓
观察理解、验证、纠错和接管过程
   ↓
用变化后的任务检查迁移表现
   ↓
由规则、教师或领域人员复核证据
```

其中，Outcome 指任务最终结果；Process 指任务中的协作行为；Transfer 指在新数据、新约束或相近新任务中的表现。三类证据应分开解释，不能用一种代替另一种。

## 四 当前项目基线

截至2026年10月17日的项目对齐记录，项目处于 R0/R0.5 合成原型、证据边界整理和研究最小闭环准备阶段。

| 事项 | 当前可确认状态 | 不能据此推断 |
| --- | --- | --- |
| 研究框架 | 已有 Foundation—Process—Transfer 问题框架和教授审阅稿 | 已证明学习效果或职业能力变化 |
| Studio | 有教师、学生、提交、复核和补正的合成流程与 React 源码 | 已通过真实用户或生产验收 |
| Agent | 当前流程以确定性或脚本化引导为主 | 已评估真实模型或真实 Agent 能力 |
| 测试 | 留有2026年9月26日本机合成测试记录 | 10月当前源码已重新通过所有测试 |
| 任务族 | Python + CSV 与 SQL/数据库诊断仍为候选 | 已冻结正式 Benchmark |
| 数据和部署 | 使用合成身份、合成任务和本机原型 | 已有真实学生数据、生产持久化或正式部署 |
| 代码执行 | 有独立安全研究材料，状态不完整 | 可以运行学生或外来项目代码 |

建立新基线时，应重新检查当前代码、运行方式和测试结果。历史记录作为历史证据保留，不替代当前重跑。

## 五 研究方案

### 核心研究问题

在职业数字任务中，学习者的基础能力与其 Agent 协作中的理解、验证、纠错和接管行为有什么关系？这些过程证据能否帮助解释学习者在变化任务中的迁移表现？

这是待检验的问题，不是已得到答案的结论。研究应允许结果不支持预期，也应记录任务无效、证据不足和反例。

### 任务研究的基本做法

先确定一个任务族，再为它建立可重复的任务材料。最小任务包应说明职业来源、任务目标、输入和约束、参考解、常见错误、可检查规则、Agent 条件、学生应说明的内容、迁移变体和不适用范围。

验证规则优先采用可检查的系统状态、程序规则或领域标准。模型自己的判断不能作为唯一正确性依据。教师或领域人员负责审查职业含义和需要人工判断的部分。

### 证据使用原则

- 最终产物说明结果，不自动证明学习发生。
- 对话和操作记录只能描述平台内可观察到的事实，不能说明学生在平台外做了什么。
- 粘贴量、调用次数、相似度和停留时间不能单独用来判断能力或诚信。
- 真实学生数据如需用于研究，应先明确研究目的、告知、授权、最小采集、去标识化、保留和退出方式。
- 研究结论须说明任务、参与者、模型条件、验证方式和适用范围。

## 六 推进阶段

本计划按阶段产物和进入条件管理。现有资料没有确认完整日历、经费和团队工时，因此不编造具体完成日期；项目负责人确认人员、资源和任务选择后，再补充日程。

| 阶段 | 主要工作 | 阶段产物 | 继续条件 |
| --- | --- | --- | --- |
| B0 项目基线 | 清点代码、文档、规格、历史证据和当前工作区；选择主要演示载体；建立当前可复跑的检查记录 | 项目资产清单、状态快照、证据索引和验证方式 | 当前源码与历史证据已分开；重要文件去向清楚；检查方法可复现 |
| R1 任务与研究方案 | 在候选中选定一个任务族；确定任务来源、参考解、正反例、检查规则、迁移变体和分析计划 | 任务包、研究问题、证据定义和分析方案 | 教师或领域人员能够审查比较内容、判断方式和可能推翻假设的结果 |
| R1.5 本机演示基线 | 仅实现支持任务走查的必要教师—学生—复核流程；重新运行对应检查 | 可重复启动的本机演示、测试记录和限制说明 | 关键流程可以复现；每项结论都有对应的检查证据 |
| R2 专家走查 | 在获得许可后，请教师或领域人员检查任务理解、证据解释和复核负担 | 走查记录、问题清单和修改建议 | 任务目标、学生责任和教师可采取的动作清楚；不把走查意见当作学习效果 |
| R3 证据复盘 | 对照研究问题检查任务效度、过程证据、迁移设计和风险 | 继续、调整或停止的决策记录 | 说明哪些判断有证据支持、哪些仍未知以及下一步所需条件 |
| R4 有条件扩展 | 根据证据单独评估第二任务族、真实模型、代码执行、身份、持久化或部署 | 独立决策、规格、安全和数据方案 | 逐项获得授权，并通过各自的成本、隐私、安全与质量门槛 |

建议顺序为 B0 → R1 → R1.5 → R2 → R3。R2 的参与者、研究数据和对外发布需要单独审批。未达到阶段条件时，先修订任务或研究方案，不以增加功能替代证据。

## 七 项目成果

项目阶段性成果以可检查的材料为主：

1. 可恢复的项目资产和证据基线。
2. 一个有来源、版本、参考解、正反例和迁移变体的职业任务包。
3. 一份说明比较方法、证据、分析方式和限制的研究方案。
4. 一条能在固定本机条件下复现的 Studio 合成演示路径。
5. 教师或领域人员走查后形成的反馈和决策记录。
6. 根据证据形成的扩展、调整或停止建议。

这些成果不自动等同于教育效果、职业技能提升、学校采用或可推广结论。

## 九 范围边界与主要风险

| 风险 | 可能影响 | 管理方式 |
| --- | --- | --- |
| 同时铺开多个任务领域 | 任务和证据难以做深 | 首阶段只选一个任务族，其他候选保留待选 |
| 任务不能代表真实职业工作 | 研究结果解释错误 | 记录任务来源并邀请领域人员审查 |
| 把平台记录当作能力结论 | 误判学生表现 | 分开呈现结果、过程和迁移证据，由教师判断 |
| 合成原型被误认为正式产品 | 对外表述超过事实 | 标注合成范围、测试日期和未验证事项 |
| 真实数据或模型调用提前开放 | 隐私、费用和合规风险 | 先做独立决策、授权和数据/安全验证 |
| 代码执行边界不完整 | 影响本机和数据安全 | 未经独立安全门槛通过，不运行学生或外来项目 |
| 人员、工时或资金不足 | 阶段延期或无法开展 | 先锁定最小交付，再确认资源和日历 |

当前不纳入范围的事项包括：完整 LMS 或成绩管理平台、AI 作弊识别、自动能力评分、真实课堂研究、未经授权的真实模型调用、运行学生或外来代码、正式身份接入、生产数据和部署。

## 十 项目管理与完成判断

每项重要工作应说明目标、允许范围、禁止范围、验收条件和检查结果。项目状态至少区分：计划中、已实现、已做结构检查、已在本机运行检查、已由实际用户或现场验证、尚未验证。不同证据不能互相替代。

阶段完成时记录产物位置、检查方式、通过与未通过内容、限制、风险和下一项决策。需要改变项目范围时，先说明原因和影响，再由项目负责人决定；不因代码已存在或测试曾经通过，就推断项目已完成。

## 十一 需要项目负责人确认的事项

1. B0 后是否按研究最小闭环优先推进；本计划建议先选定一个任务族和研究方案。
2. 首个任务族选择 Python + CSV，还是 SQL/数据库诊断。
3. 是否将 `apps/studio-web/` 确认为主要演示载体。
4. 何时邀请教师或领域人员走查，以及走查是否记录可识别信息。
5. 阶段负责人、工时、经费和目标日期。

在这些事项确认前，任务族、日历、经费和真实参与者安排保持待定。
