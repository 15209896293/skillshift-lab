## 2. 可逐行手算的合成任务

### 2.1 业务问题与业务口径

**业务问题：**“按 `order_date` 统计已支付订单的订单数、订单金额和不同客户数。每张符合条件的订单只能贡献一次订单金额；查看订单有几条明细不能改变订单金额。”

本题先锁定的业务口径是：

- **订单粒度**：`orders` 的一行是一张订单；`amount` 是该订单的完整订单金额，不是单件金额。
- **明细粒度**：`order_items` 的一行是一种订单明细。一个订单可有零到多行明细。
- **统计粒度**：按订单日期、仅 `status = 'paid'`，每张订单一次；金额为这些订单 `amount` 之和；客户数为这些订单的不同 `customer_id` 数。
- 本例的订单金额不从明细金额重算；若业务要计算“商品件数”或“按明细金额计销售额”，那是另一项指标，必须另写口径。

### 2.2 表结构（示意）

```sql
orders(
  order_id    varchar primary key,
  customer_id varchar not null,
  order_date  date not null,
  status      varchar not null,
  amount      decimal(10,2) not null
)

order_items(
  item_id     varchar primary key,
  order_id    varchar not null references orders(order_id),
  product     varchar not null,
  quantity    int not null
)
```

### 2.3 合成数据

`orders`：

| order_id | customer_id | order_date | status | amount |
|---|---|---|---|---:|
| O101 | C01 | 2026-04-01 | paid | 100.00 |
| O102 | C02 | 2026-04-01 | paid | 100.00 |
| O103 | C01 | 2026-04-01 | paid | 50.00 |
| O104 | C03 | 2026-04-01 | pending | 80.00 |

`order_items`：

| item_id | order_id | product | quantity |
|---|---|---|---:|
| I01 | O101 | keyboard | 1 |
| I02 | O101 | mouse | 1 |
| I03 | O102 | monitor | 1 |
| I04 | O103 | cable | 2 |
| I05 | O103 | adapter | 1 |

| I07 | O104 | charger | 1 |

### 2.4 手工推导的独立答案

先不看任何候选 SQL，只从写明的业务口径挑出已支付订单：`O101`、`O102`、`O103`。

- 订单数：`3`。
- 订单金额：`100.00 + 100.00 + 50.00 = 250.00`。
- 不同客户数：`{C01, C02} = 2`。

因此 2026-04-01 的预期结果是：`paid_order_count = 3`，`paid_amount = 250.00`，`paid_customer_count = 2`。这是本规格的独立业务口径答案；它不是复制任何候选查询的输出。

## 3. 正确方案、错误方案与必须暂缓的情形

### 3.1 方案 A：直接连接明细后重复累计（错误）

```sql
SELECT o.order_date,
       COUNT(*) AS paid_order_count,
       SUM(o.amount) AS paid_amount,
       COUNT(DISTINCT o.customer_id) AS paid_customer_count
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id
WHERE o.status = 'paid'
GROUP BY o.order_date;
```

连接后的已支付行是 `O101, O101, O102, O103, O103, O103`：

- `O101` 有两条明细，`100.00` 被加两次；
- `O102` 有一条明细，`100.00` 加一次；
- `O103` 有三条明细，`50.00` 被加三次。

所以该 SQL 得到行数 `6`、金额 `450.00`，而不是 `3` 和 `250.00`。`COUNT(DISTINCT o.customer_id)` 仍可能偶然给出 `2`，正说明一个输出列正确不能推出整条聚合正确。这里暴露错误所必需的数据特征是：至少一个订单有多条明细，且被重复的订单金额参与 `SUM(o.amount)`。

### 3.2 方案 B：用 `SUM(DISTINCT amount)` “修复”（仍错误）

```sql
SELECT o.order_date,
       COUNT(*) AS joined_row_count,
       SUM(DISTINCT o.amount) AS paid_amount
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id
WHERE o.status = 'paid'
GROUP BY o.order_date;
```

这会把连接后反复出现的 `100.00` 和 `50.00` 去重为 `100.00 + 50.00 = 150.00`。它没有识别“同一订单被复制”，而是按**金额值**合并：`O101` 与 `O102` 是两张不同的 100.00 订单，却被错误地当作一笔。因此结果 `150.00` 仍非正确的 `250.00`，且连接行数还是 `6`。本例特意设置两张同金额订单，正是为了使这种看似合理的修复暴露错误。

### 3.3 方案 C：先在订单粒度聚合（正确）

```sql
SELECT order_date,
       COUNT(*) AS paid_order_count,
       SUM(amount) AS paid_amount,
       COUNT(DISTINCT customer_id) AS paid_customer_count
FROM orders
WHERE status = 'paid'
GROUP BY order_date;
```

本问题所需的三个指标全来自订单粒度，因此没有理由先连接明细。每一张符合条件订单恰出现一次，结果为 `3 / 250.00 / 2`。

### 3.4 方案 D：必须用明细信息时的正确替代实现

如果报告还要展示“每张订单有几条明细”，可以先把明细压回一行一订单，再做订单级统计：

```sql
WITH items_per_order AS (
  SELECT order_id, COUNT(*) AS item_line_count
  FROM order_items
  GROUP BY order_id
)
SELECT o.order_date,
       COUNT(*) AS paid_order_count,
       SUM(o.amount) AS paid_amount,
       COUNT(DISTINCT o.customer_id) AS paid_customer_count,
       SUM(COALESCE(i.item_line_count, 0)) AS item_line_count
FROM orders AS o
LEFT JOIN items_per_order AS i ON i.order_id = o.order_id
WHERE o.status = 'paid'
GROUP BY o.order_date;
```

`items_per_order` 保证每个 `order_id` 至多一行，`LEFT JOIN` 也不会因为一张已支付订单暂时没有明细而丢失该订单。订单级三个指标仍为 `3 / 250.00 / 2`；本例的明细行数为 `2 + 1 + 3 = 6`。此方案不是因为多写了 CTE 而正确，而是因为连接两侧都已满足“一行一订单”。

### 3.5 不能自行猜测、应先补充信息的情形

下列情形下，学习者应选择“暂缓”或“需澄清”，而非强行修 SQL：

| 未明确信息 | 为什么会改变答案/查询 | 需要补充什么 |
|---|---|---|
| `amount` 是否含税、运费、退款，或应由明细单价乘数量计算 | 决定订单表金额是否就是所求销售额 | 指标定义、退款规则、金额字段来源与时间点 |
| “订单数”是否包含 pending、cancelled 或部分退款订单 | 决定筛选条件 | 订单状态字典和统计期间规则 |
| “商品件数”是否也是问题的一部分 | 这是明细粒度指标，不能用订单金额的口径替代 | 需报的指标清单和每一指标的粒度 |
| 订单没有明细是数据异常还是允许的业务状态 | 决定 `INNER JOIN` 是否会不当漏掉订单 | 完整性约束及缺失行处理规则 |

## 4. 学习者提交的可核验证据

学习者不得只交最终 SQL 和三个数字。每一提交至少包括下表字段；使用结构是为了保留推理可审查性，而不是要求术语背诵。

| 提交字段 | 学习者应给出的内容 | 测量什么 | 如何避免把术语背诵当理解 |
|---|---|---|---|
| `decision` | 对候选结果选择 `accept`、`reject`、`modify` 或 `defer` | 是否在证据不足时能作出可追踪判断 | 不以选择词本身评分；须与后续数据/口径证据一致。 |
| `metric_spec` | 指明对象粒度、日期、状态、每订单是否仅一次、金额字段含义 | 是否能把业务口径和行粒度分开 | 量规要求绑定 `orders` 或 `order_items` 的具体列和本例订单行。 |
| `claimed_result` | 候选结果与自己接受/修改后的结果 | 是否能报告可复查结论 | 数值由独立口径表比对，不只检查格式。 |
| `verification_query_or_manual_check` | 订单表基线查询、按 `order_id` 的连接行计数，或逐行手算 | 是否采用能揭示重复的检查 | 必须给出例如 `O101=2`、`O103=3` 或同等反例，单写“检查 JOIN”不得分。 |
| `reasoning` | 说明哪一行在连接后被复制、为何影响某个聚合列 | 是否能用数据解释接受/拒绝 | 对照具体数据关系评分；出现“一对多”“DISTINCT”等词不自动得分。 |
| `revision` | 若修改，给出修订 SQL/伪代码及为何恢复一行一订单 | 是否能提出与口径相符的替代实现 | 结果正确但无法说明粒度，解释项不能自动通过。 |
| `uncertainties` | 仍未解决的字段、状态、退款或缺失明细问题 | 是否能识别不能由 SQL 自行决定的业务问题 | 仅当它指出一个题面未给出的具体事实、给出至少两种合理解释，并说明二者会改变查询、筛选或预期结果时，才计为有效暂缓依据；凭空堆砌风险不得分。 |

建议将 `decision` 分为两段记录：先对候选输出作判断，再在写明口径后说明是否改变判断。这样能区分“结果碰巧正确”与“理由可复核”。

**暂缓评分条件：**本规格第 2 节已经给定 `amount` 为订单完整金额、仅统计 `paid`，且三个输出指标均已定义。因此面对本节的完整合成题，单独选择 `defer` 不正确，不能因“谨慎”得分。只有任务题面故意留下会实质改变答案的业务条件时，才可接受暂缓；提交必须逐项列出缺失事实、两种可行口径及各自会改变的查询或结果。若列出的不确定性不改变答案，或题面已经明确该条件，暂缓应按错误拒绝处理。该规则既防止把无关迟疑当能力，也不强迫学习者替业务方臆定口径。

## 5. 独立验证与反例测试矩阵

### 5.1 独立答案的生成方式

验收答案须先由书面业务规格和 `orders` 的三张已支付订单手工/独立表格推导为 `3 / 250.00 / 2`，再比较候选 SQL。不得把候选 SQL、其输出或同一作者写的预期文件当成唯一真值来源。当前没有指定独立审查者，故本规格**不声称已完成独立验证**。

| 情形/候选结论 | 按独立口径的预期 | 错误接受风险 | 错误拒绝风险 | 检查办法 | 可机器判部分 | 需量规复核部分 |
|---|---|---|---|---|---|---|
| 直接连接后报 `6 / 450.00 / 2`，并称正确 | 应拒绝该金额/订单数 | 只看客户数会误接受整条结果 | 若题目实际问明细行数，误用本题口径会误拒绝 | 列出 `O101` 两行、`O103` 三行；对照订单基线 | 数值、连接行数、状态筛选 | 是否说明这些重复为何影响订单金额 |
| `SUM(DISTINCT amount)` 后报金额 `150.00` | 应拒绝 | 未包含同金额订单的夹具会误接受 | 若业务确实要“金额值集合”会误拒绝不同指标 | 检查两张独立的 100.00 订单 | 数值与预期不符 | 是否说清按金额去重与按订单去重不同 |
| 订单表方案 C 报 `3 / 250.00 / 2` | 应接受（限本题口径） | 未检查状态/日期可能在其他数据上误接受 | 若业务要求基于明细金额，可能误拒绝另一正确计算 | 订单 ID、状态、手工求和与日期分组 | SQL 结果、字段与数值 | 对业务口径是否作了恰当限定 |
| 明细先聚合、再 `LEFT JOIN` 的方案 D 报同一订单级结果 | 应接受（限所写口径） | 子查询未真正在订单粒度聚合会漏检 | 若仅因写法不同而拒绝会错杀正确方案 | 验证中间结果每个 `order_id` 最多一行；含无明细订单的变异例 | 基数检查、数值 | 是否解释 `LEFT JOIN` 与明细缺失的关系 |
| 在题面确有退款、状态或金额含义缺口时选择 `defer` | 仅在缺口会改变查询/答案时接受；本节完整合成题不接受 `defer` | 把合理暂缓当作能力不足 | 接受无关的泛化迟疑，或在题面已明确时错误拒绝 | 核对缺失事实、两种可行口径和结果/查询差异；不能只援引第 3.5 节的词表 | 可提示是否给出全部必填字段；不能机器判定业务解释合理性 | 缺口是否真实存在、两种解释是否合理且是否实质改变口径 |

机器检查只能比较结构化结果、枚举值、SQL 是否可解析、反例中订单/行数是否对应，以及中间结果是否满足“一订单至多一行”。解释是否真实关联业务口径、是否选择了合理的暂缓，需由可见量规复核。若无独立审查者，应如实标记为“机器和同一审查链自检”，不能改称独立验证。

## 6. 廉价基线与候选结构化训练的具体差别

在本例上，基线 A 与候选 B 的比较对象不是“有没有 Agent”，而是同一通用 Agent 协作场景下，额外的结构化核验流程是否带来可观察的净收益。

| 方案 | 在本例提供什么 | 不能预设什么 | 未来可比较的指标 |
|---|---|---|---|
| A：通用 Agent + 一页核验清单 | Agent 可提议 SQL；清单要求：写出指标粒度、先算 `orders` 基线、检查 `JOIN` 后每个订单的行数、用同金额订单检查 `SUM(DISTINCT)`、记录未知业务口径。 | 清单被阅读不等于执行，且不自动产生可审查证据。 | 正确接受/拒绝率、错误接受/错误拒绝、完成时间、遗漏的核验步骤。 |
| B：候选结构化训练 | 除 A 的提示外，要求填第 4 节的判断、口径、反例、修订与不确定性；反馈按可见量规指出“哪张订单、哪一指标、哪条证据”不一致，并要求在提交前形成订单粒度的独立答案。 | 若只是把 A 的清单重排成表单、没有反例/量规反馈/可审查修订，则 B 只是展示方式变化，不能预设额外价值。 | 与 A 共用的迁移结局：独立答案正确性、判断恰当性、反例与判断的一致性、用时与负担；不得用 B 的专用表单完成度作为额外收益。 |

**A/B 的共同迁移测量：**若未来获授权比较 A 与 B，二者都必须完成同一份版本冻结、未用于开发或训练的保留任务，并面对相同的业务规格、夹具、候选 Agent 输出、可用查询权限、时限与答题界面。支持条件可以不同（A 的一页清单，B 的结构化训练），但结局测量不得不同：两组均以同一份中立的迁移提交格式和同一盲审量规评估“独立推导的订单级答案是否正确、对候选结果的接受/拒绝/修改/暂缓是否恰当、所引反例是否真的支持该判断、以及用时与负担”。评分时不因 B 在训练阶段多填字段而奖励其格式，也不因 A 没有 B 的专用表单而扣分。这样测量的是能否迁移到新任务的核验与纠错，而不是谁更熟悉某个表单。

未来比较需要同时报告帮助与负担：B 若在上述共同迁移测量中稍增正确率却显著增加时间、无关填写或错误暂缓，不能仅以正确率宣称更优；小样本无明显差异也只表示估计不稳定，不能宣布训练无效。任何效果估计须另有参与者、同意、隐私和方法授权。

## 7. 最小实验工具申请草案（仅设计）

### 7.1 不做工具仍能验证什么

无需工具即可对本方法包做文档级审查：手工复算示例、检查每种错误确实由数据触发、审查业务口径/量规、比较 A 与 B 的内容差异、设计独立答案和未来保留测试。它不能回答真实使用时 Agent 输出如何被接受、结构化证据是否降低错误、负担多大或权限隔离是否实际生效。

### 7.2 确实需工具才能回答什么

若以后获授权，要检验在受控环境中“候选 SQL、核验动作、修订版本和结果”是否可重复记录，以及在隐蔽变异夹具上 A/B 的表现和负担，才需要最小实验工具。工具不是完整教学平台，也不应以实现工具作为先决条件来声称方法有效。

### 7.3 最小功能、输入输出与成本项

| 项目 | 最小设计（非实施承诺） |
|---|---|
| 单一任务包 | 仅一个版本化 SQL 任务：业务规格、只读夹具、开发样例/保留测试标记、独立答案和可见量规。 |
| 输入 | 学习者提交的 SQL/伪代码、结构化证据字段、必要的非敏感操作时间戳；Agent 文本只有在另行同意且最小化后才可记录。 |
| 输出 | 候选结果与独立预期的机器比较、基数/反例检查、供人工复核的证据包；不输出人格化评分、排行榜或“AI 替代率”。 |
| 最少执行面 | 一个隔离数据库夹具和一个提交区；没有账号体系、多角色管理、多节点、排行榜、课程平台或生产业务连接。 |
| 成本项 | 夹具维护、隔离计算资源、人工量规复核时间、版本/日志保存、安全审查、参与者时间；若未来接入外部模型，另列模型/数据传输成本和授权，不能默认调用。 |

### 7.4 权限与数据边界

- 夹具数据库由环境初始化身份创建；学生或候选查询身份只能读取指定夹具，不能写入、删除或改表。
- 可写提交区与只读夹具分离：提交文本/结果写入受限目录或独立提交表，不能借此获得对夹具、系统表、其他参与者或主机文件的权限。
- `root` 仅可用于确有必要的环境初始化、创建受限账户和销毁临时环境；它不能替代学生/候选执行身份。现有脚本以 root 运行候选提交的事实，在未来实施前必须单列为待解决的契约偏差，而不能以“已跑通”覆盖。
- 禁止采集真实学生身份、联系方式、学号、设备全盘信息、私人文件、真实凭据、无关屏幕/聊天内容、生产数据库数据，以及超出本任务所需的 Agent 对话内容。

### 7.5 实现前仍待决定的事项

1. 谁提供参与者同意、隐私说明、数据保留期限与退出机制；本规格不替代这些决定。
2. 是否需要任何外部 Agent、其版本/提示/数据传输边界如何冻结；未获授权前不调用。
3. 数据库引擎、隔离方式、账户创建流程和故障清理如何经安全审查；不能把 root 运行当成完成最小权限。
4. 独立答案和解释量规由谁审查；没有独立审查者时如何如实报告局限。
5. 保留测试、随机化/平衡和分析计划如何在接触结果前冻结；不设无依据的参与者人数门槛，也不把时间间隔当作携带效应消除保证。

## 8. 本轮结论与下一步界限

本方法包满足“一个具体、可手工复算的 SQL 聚合诊断题”的设计目标：直接连接和 `SUM(DISTINCT amount)` 都被具体数据揭示，订单粒度方案和预聚合替代方案有明确适用条件，机器检查、人工量规与尚未验证内容分别列出。它支持后续审查方法是否足够清楚，不支持任何用户研究、训练增益、独立验证已经完成，亦不构成实现授权。

下一步如需推进，应先由统筹另行决定是否批准：公开任务筛选/许可复核、独立答案审查、访谈或参与者材料准备、以及最小实验工具实现。未经该授权，项目应停留在方法设计与只读证据复核阶段。
