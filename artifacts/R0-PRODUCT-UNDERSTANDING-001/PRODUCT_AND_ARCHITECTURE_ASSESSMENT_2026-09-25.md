## 1. 执行摘要

SkillShift Lab 的研究主线是理解 Agent 如何改变职业教育中的任务、基础能力和人机协作，以及学生如何把已有基础迁移到 Agent 协作场景。SkillShift Studio 是承载该研究问题的教学产品与研究基础设施，不是研究结论本身。

Studio 的产品候选价值：教师能够低负担地布置允许 AI 协作的职业实践任务；学生在任务环境中使用 Agent 形成实际交付，并承担必要的验证、解释、纠错、接管或补正；教师能够根据有限、可解释且与任务相关的证据给出反馈。系统不阻止学生使用外部 AI，不监控无关行为，也不自动判断作弊、能力或学习效果。

上述价值目前仍是**待验证的产品假设**。现有 Gate A 只证明一段本机、合成、确定性的任务状态与反馈流程可运行。它不包含真实 LLM、代码工作区或真实用户证据，因此不能证明通用教育 Agent 产品已成形。

## 2. 项目到底在做什么

### 2.1 研究主体：SkillShift Lab

核心研究问题是 Agent 进入职业教育后：

1. 职业任务与知识结构发生什么变化；
2. 学生仍需具备哪些基础技能；
3. 学生如何委托、判断、验证、纠错和接管 Agent 工作；
4. Foundation Track 与 Agent Track 中的任务表现和过程条件如何比较。

R0 产品数据默认只是运营/教学数据，不会自动成为研究数据。研究使用须单独定义目的、授权、最小字段、去标识化、访问与保留规则。

### 2.2 产品载体：SkillShift Studio

Studio 应提供真实类型的教学任务、适当的 Agent 协作方式、可交付成果、任务所需的最小过程证据，以及教师和学生之间的反馈/补正机制。产品的差异化不应是“模型比通用 Agent 更聪明”，而应是任务和教学过程的组织与可复核性。

### 2.3 首个使用切口

当前项目文件把高职大数据、计算机、软件相关学习者和教师/导师作为首批反馈对象，把 Python + CSV 作为一个 Golden Path。它是验证切口，不是永久产品边界，也不是已获得当地课程或用户需求验证的事实。

## 4. 产品提供什么

### 4.1 学生侧：任务内 Agent 工作空间

学生首先看到“我正在完成什么任务、下一步可做什么、Agent 能做什么、我要亲自负责什么”。Agent 应围绕当前任务和材料协作，而非只提供脱离任务的聊天框。

对于编程类任务，候选体验需考虑项目文件、代码编辑、Agent 对话/计划、代码差异、运行或验证结果、学生确认/拒绝/接管、最终提交说明。对于非编程任务，应由任务类型适配相应工作材料与 Artifact；Python 编辑器不能成为全产品的固定模型。

“运行代码”和“Agent 直接读写项目”是高风险执行能力，不因界面存在就自动获准。当前 Foundation Spike 未通过足以支持学生项目执行的安全门槛。

### 4.2 教师侧：任务设计与可解释复核

教师创建时选择/描述任务、交付要求和平台级 Agent 协作方式；系统提供简单默认值，不要求教师编写权限策略或监控规则。发布时向学生说明 AI 可做什么、哪些任务内事实会被记录、教师能看到什么以及如何解释/补正。

复核界面聚焦提交产物、任务要求的验证与说明、少量可追溯过程事实、已知限制和教师可执行动作。`REVIEW_REQUIRED` 表示“请教师查看”，不得表达为违规或能力不足。教师作最终判断，学生可解释、补证、补正或重交。

### 4.3 平台服务与管理

平台服务负责任务/版本、身份与授权、会话、模型网关、费用许可、事件引用、提交包、教师反馈和数据生命周期。最小后台管理只支持运营必要配置；完整 LMS、成绩册、班级画像、大规模分析不是当前必需。

## 5. 建议的产品结构（Proposed）

```text
教师 Web
  创建/发布任务 → 复核队列 → 反馈与补正
          │ API / 任务、权限、会话、提交、事件引用
平台控制面
  身份与任务服务 + Agent 编排/模型网关 + 预算/审计/持久存储
          │ 仅对明确授权的任务范围发起工作
学生 Studio / 学习工作台
  任务上下文 + Agent 协作 + 学生确认/接管 + 提交
          │ 若任务需执行代码：经独立选定和验证的执行边界
隔离执行面（当前未选型、未通过安全验证）
  与控制面隔离；不得由现有 ECS 执行任意学生代码
```

教师 Web、学生工作台、平台 API 和代码执行面是不同责任面。界面可能统一品牌，但身份、权限、故障域和安全边界不能混成单页演示。学生工作台采用桌面应用还是浏览器 IDE，取决于代码文件与执行方案，当前没有足够证据定案。

## 6. 当前状态与证据边界

### 已确认或已有局部证据

- 产品重定位：研究主线下的教学工作平台，不与 Codex/Cursor 比通用 Agent 能力；教师最终判断，学生可补正。
- 首条 Agent-first 交付边界：`docs/product/R0_AGENT_FIRST_DELIVERY_DECISION.md` / ADR-004 已接受；合成首条闭环不访问、修改或执行学生本机项目。
- Gate A：状态机、确定性引导、模拟角色、教师反馈和补正等合成流程有代码、测试和 Artifact。相关规格为 `specs/R0-AGENT-FIRST-VERTICAL-SLICE/README.md`。
- 模型路线：不使用 OpenAI API；国产多模型服务端网关边界已记录，首个候选供应商 DeepSeek，月预算上限 100 元。但没有真实 Key、真实请求或可对账生产账本。
- ECS：只作为未来控制面候选；禁止执行任意学生代码。部署清单仍为 0/28 关闭。

### 未验证或未实现

- 教师/学生是否有文档描述的真实痛点，真实使用是否低负担、有价值；没有真实需求访谈或产品试用证据。
- 具备通用模型理解能力的教育 Agent；现有 `ScriptedGuidanceAdapter` 是确定性模拟，不是 LLM。
- 正式教师 Web / 学生独立工作台、账号/多用户授权、生产后端/数据库、模型真实调用。
- 学生本机文件操作、代码编辑/运行、自动修改/命令工具；Foundation Spike 对未来执行路线仍 PARTIAL。
- 真实数据用途、生产保留政策、真实部署、课堂效果、学习收益或采购意愿。

因此，Gate A 的 `PASS` 只对合成工作流的验收范围成立；Gate B 与 Foundation Spike 仍 PARTIAL；生产控制面不可部署。

## 7. 关于“教师端 → 学生端 → 后台”的独立判断

这个顺序适合作为**产品理解与体验设计顺序**：

1. 先定义教师从布置到复核/补正的闭环，因为教师负责任务约束和最终反馈；
2. 再定义学生如何真实完成任务并使用 Agent，因为这是产品交付价值中心，不能被教师后台替代；
3. 然后明确后台和管理端如何支持两条工作流。

但它不适合作为**软件依赖顺序**，不能把数据模型、API 契约、身份/授权、事件版本和执行安全全部拖到两个前端之后。建议先冻结这些契约的最小版本，然后分别做教师和学生界面原型，最后实现并连接一个纵向闭环。

建议开发阶段顺序：

1. 产品定义与单任务契约；
2. 教师端交互原型（任务模板、协作模式、学生责任、提交要求、复核/补正）；
3. 学生端交互原型（任务上下文、Agent、成果区、验证/提交；编程切片再包含编辑器与差异视图）；
4. 后端接口、数据模型与权限/事件契约的定稿；
5. 以教师创建 → 学生协作/提交 → 教师反馈 → 学生补正为一条集成纵向切片；后台管理只补最小运行配置；
6. 真实模型、代码执行、真实用户与部署各自通过独立 Gate 后才能接入。

界面原型可先用合成数据和假适配器，但必须明确标记为交互/视觉验证；不可将它称作可用 Agent、持久后台或安全运行环境。

### 首个产品切片的关键决策

当前 Accepted ADR-004 / Active `REQUIREMENTS_SPEC.md` 将本机文件和代码执行排除在首条 Gate A 闭环之外。若后续目标是交付大众熟悉的项目型编程 Agent 工作体验，则该边界只能通过正式决策与版本化规格变更调整，不能以界面设计或代码实现暗中绕过。

| 方案 | 内容 | 主要收益 | 主要代价/限制 |
| --- | --- | --- | --- |
| A. 保持当前首条 R0 | 先交付无代码、无真实模型的任务对话与提交/复核/补正闭环；编程工作区另列后续阶段。 | 不触发代码执行安全和运行环境选型；能单独评估教师流程。 | 仍不能证明学生在真实职业项目中如何与 Agent 协作；与完整编程工作台的距离较大。 |
| B. 把首个产品切片改为项目型编程 Agent | 以一个合成 Python + CSV 任务贯穿教师布置、学生工作区、Agent 协作、成果验证和教师反馈；代码执行 Provider 作为独立前置 Gate，在验证前不得运行外来/学生代码。 | 直接验证项目定位中的任务协作、学生检查/接管和教师复核；界面和系统更贴近真实代码 Agent 产品。 | 需要修改 ADR-004 / Active 规格；实现进度受执行边界、真实模型与数据 Gate 制约；短期只能先做视觉/交互原型或假运行接口。 |

**主控建议：选择 B 作为目标产品切片，但分阶段兑现能力。**先以教师任务流程和学生编码工作台完成一条真实产品交互规格；API/数据契约同步定义；真实模型与代码执行不假装已就绪，分别保持默认拒绝并通过独立 Gate 后再接入。如此仍不要求产品在 Agent 能力上胜过 Cursor/Codex，目标只是让学生在职业任务上下文中使用 Agent，并让验证、解释、接管、提交与教师反馈形成产品闭环。

此建议会改变现有首条 R0 的范围，**需要项目负责人确认方案 A 或 B，或提出等效边界**。在此之前，只继续证据盘点和非实现性分析，不改 ADR/Active 规格、不实现代码工作区、不选执行 Provider。
