# SkillShift Studio R0 需求规范

## 文档状态与效力

- 状态：**Active**（2026-09-24）；定义 R0 单一产品闭环的需求基线，不代表任何功能已经实现。
- 上游：`R0_PRODUCT_REPOSITIONING_DECISION.md`、`R0_RESEARCH_TASK_EVIDENCE_CONTRACT.md`、`TEACHER_ASSIGNMENT_REVIEW_REMIDIATION_WORKFLOW.md`。
- 下游：R0 ADR、`specs/R0-FOUNDATION-SPIKE/`、技术规范、质量规范、测试计划和验收记录。
- 冲突处理：本文件取代此前“通用 AI Agent Workspace、教师端不做”的 R0 需求表述；V3.0 总纲仍保留为 Draft，发生冲突时遵循产品重定位决策。
- 非目标：完整 LMS、正式课堂成绩处理、外部 AI 检测、全桌面监控、学生能力自动画像、正式研究实验或与主流 Agent 的能力竞争。

## 1. 产品背景与 R0 首要验证目标

SkillShift Lab 研究 Agent 对职业教育知识、能力、任务结构和人机协同的影响。Studio 是提供真实任务、受控 AI 协作、过程证据和教师干预入口的产品化研究基础设施。

R0 不先证明学习效果或研究结论。它优先验证两件产品事实：

1. **教师/导师低负担闭环（A）**：教师是否能完成一次创建、一次基于理由的复核和一次反馈/补正，而不是查看全量日志。
2. **学生有效参与闭环（B）**：在允许 Agent 协作时，学生是否能完成与任务绑定的验证、解释、纠错、接管或补正，而非只等待 Agent 产出。

Python 是首个 Code Workspace Evidence Adapter 的验证环境，不是产品永久只支持 Python 的承诺，也不能代表 PyCharm、虚拟机或其他职业教学场景。

## 2. 用户、角色与最小价值

| 角色 | R0 要完成的任务 | 获得的直接价值 | 不应假定 |
| --- | --- | --- | --- |
| 教师/导师 | 创建一项允许 AI 协作的练习；查看少量待复核提交；反馈或补正。 | 有限、可解释的过程摘要和教学动作。 | 已有学校采购、正式课堂授权或完整教务系统。 |
| 学生 | 安装/启动 Studio；在绑定 Workspace 完成任务；使用 Agent；提交验证与说明；回应反馈。 | 已配置任务环境、基础 Agent 能力、可恢复的运行过程与补正机会。 | 平台能观察其所有设备、所有 AI 使用或真实能力。 |
| 平台运营者 | 提供任务、服务、Node 版本和必要故障支持。 | 可验证 R0 是否可用的运营事实。 | 可将运营日志自动用于研究或评分。 |

R0 仅面向合成任务、负责人自有材料和后续明确告知的非计分自愿练习；不得假定每个学生拥有可自由安装软件的个人电脑。

## 3. R0 端形态与范围

```text
教师/导师 Web 端
  任务创建、协作模式选择、复核队列、反馈与补正状态
        ↓
平台服务端
  身份、任务、提交、Agent/模型网关、最小事件、Artifact 提交包元数据
        ↓
学生桌面 Studio / Agent Node
  绑定 Workspace、基础 Agent、受限 Python 运行、权限确认、停止/接管、事件采集
```

### 3.1 R0 必须具备

1. 教师创建一项模板化、非计分、允许 AI 协作的任务，并选择一种固定协作模式。
2. 学生可在已绑定的本机 Workspace 中接收任务材料、启动或恢复任务。
3. 学生可使用基础 Agent 完成项目内的读取、计划、文件修改、受控命令运行和失败解释；所有操作均在 Workspace 边界内。
4. 学生始终可查看当前动作、暂停、停止或接管 Agent Run。
5. 任务至少要求一次可复现的结果验证，以及一次任务关联的人类责任：解释、纠错、接管、验证或补正之一。
6. 系统生成最小提交包：任务/环境/Node/Agent 版本、选定 Artifact 的哈希与元数据、验证结果、必要事件引用和学生提交说明。
7. 教师仅通过可解释的复核理由查看提交，并能认可、请求说明、请求补证、请求补正或标记环境问题。
8. 学生可看到与自身有关的理由和证据范围，并可说明、补证、补正或重新提交。
9. 产品运营数据与研究数据分离；不自动生成成绩、能力结论、作弊结论或研究结论。

### 3.2 固定协作模式

| 模式 | R0 Agent 权限 | 学生默认责任 |
| --- | --- | --- |
| 仅问答 | 解释、讨论；不直接操作项目。 | 自行运行或提交自己的修改。 |
| 协作需确认 | 读取、计划和修改；关键动作由学生确认。 | 确认关键计划/修改，并完成结果验证。 |
| 自主协作 | 在绑定 Workspace 内读写、运行和执行已允许工具；不拥有宿主机权限。 | 查看结果并完成一次验证说明、纠错、接管或补正。 |

自主协作不等于“完全访问”。依赖安装、网络、版本控制和其他高危命令必须经 Workspace 策略允许；R0 不向学生 Node 储存模型 API Key。

### 3.3 明确不做

- 任意本机目录、私人文件、全桌面、键盘记录、浏览历史、手机活动或其他应用监控；
- 外部 AI 使用检测、相似度定性、隐藏风险分、自动扣分或自动作弊结论；
- 完整课程管理、成绩册、学校统一账号、支付、正式多租户部署；
- 替代 PyCharm、虚拟机、数据库教学环境或成为全功能 IDE；
- 使用真实学生隐私数据、将产品日志直接导出为研究结论。

## 4. 作业、参与和提交状态

R0 最小参与关系为：教师/导师创建任务 → 通过受控邀请或任务码让学生加入 → 学生在一台已注册 Node 上绑定 Workspace → 提交或补正。完整班级、选课与教务同步不在 R0。

```text
DRAFT
→ ASSIGNED
→ IN_PROGRESS
→ SUBMITTED
→ REVIEW_REQUIRED（存在可解释待复核理由）
→ FEEDBACK_REQUIRED
→ RESUBMITTED
→ CLOSED
```

`REVIEW_REQUIRED` 不表示违规；`CLOSED` 不表示能力评定或成绩。Node 离线、环境失败、版本不兼容或同步不完整必须显示为独立状态，不能伪装成学生过程不足。

## 5. 证据、Artifact 与本机数据边界

### 5.1 可观察事实

R0 可记录任务配置、平台内 Agent 动作、文件差异摘要、平台内粘贴事件、命令结果、错误、验证结果、Artifact 元数据、提交和教师反馈。每一项待复核理由必须展示触发事实、规则、已知不可观察边界和可用教师动作。

这些事实仅支持教师提出说明、补证、补正或环境处理；不得推断外部 AI 来源、学生真实理解、独立完成或作弊。

### 5.2 提交包与可复核性

学生本机工作目录默认不整体上传。一次提交必须生成最小、可定位的提交包，并同步其元数据与经任务允许的 Artifact：

- 任务、任务模板和验证器版本；
- Node、运行环境、Agent Runtime 和模型引用版本；
- 结果验证命令、退出状态和输出摘要；
- 选定 Artifact 的相对路径、哈希、大小和任务允许的副本/导出；
- 事件序列引用、提交时间和同步状态；
- 学生说明、教师反馈与补正关系。

具体 Artifact 副本、保留期限、删除/退出和研究导出规则由 ADR-003 与后续校内治理确认。同步失败必须可见、可重试，且不得把本机路径当作服务端已可复核的 Artifact。

## 6. 最小 Agent 能力与控制要求

R0 的 Agent 不是通用本机自动化工具。它至少应在绑定 Workspace 内支持：`list_files`、`read_file`、`search_files`、`write_file`、`run_command`、`inspect_environment`、`stop_run`。

每次行动必须关联任务、Workspace、Agent Run、模式、工具版本、输入摘要、结果、开始/结束时间和退出状态。学生端必须显示计划、当前动作、失败与最终状态；停止或接管后不得继续启动后续工具行动。

模型供应商、模型版本、服务端/本机推理位置、成本和可用性尚未选定。未选定前，不得将真实学生数据发送给第三方模型，也不得把模型能力写入验收结论。

## 7. 验收标准

| ID | 条件 | 最小证据 |
| --- | --- | --- |
| AC-R0-01 | 教师可用固定模板创建任务并选择协作模式，无需配置监控或评分公式。 | 合成端到端演示和状态记录。 |
| AC-R0-02 | 学生可在已注册 Node 的绑定 Workspace 中接收、启动、恢复和提交任务。 | Node/任务集成测试。 |
| AC-R0-03 | Agent 仅能访问允许 Workspace，越界路径、其他 Workspace 与私人目录被拒绝并记录。 | 安全负向测试。 |
| AC-R0-04 | 学生能在运行中查看、暂停、停止或接管 Agent；停止后无后续工具行动。 | 状态机与进程树测试。 |
| AC-R0-05 | 冻结的合成 Python 任务可完成“故障/要求 → 协作 → 运行验证 → Artifact → 提交”的闭环。 | 可复现运行记录、哈希和提交包。 |
| AC-R0-06 | 每项任务至少出现一次任务关联的人类责任，并可在提交包中定位。 | 合成案例与教师复核记录。 |
| AC-R0-07 | 待复核项均显示事实、规则、不可观察边界和教师动作；不生成作弊/能力结论。 | 界面验收与规则测试。 |
| AC-R0-08 | 教师可完成认可、请求说明、补证、补正和环境问题五种处理，学生可完成相应后续路径。 | 八类合成工作流案例。 |
| AC-R0-09 | 提交包可定位任务/环境/Node/Agent/验证器版本及 Artifact 哈希；同步失败可见。 | 提交包 Schema 与恢复测试。 |
| AC-R0-10 | 不采集全桌面、私人目录、真实凭据或无关浏览信息；运营数据不自动进入研究导出。 | 数据字段审计与权限测试。 |
| AC-R0-11 | Node 安装、无管理员权限、断网恢复、版本不兼容和环境失败均有明确状态或恢复路径。 | 受控环境测试与人工验收。 |

## 8. R0 成功、停止与研究边界

R0 观察教师是否理解并愿意处理摘要、教师单次处理是否可接受、学生是否能完成基础流程和人类责任、Artifact 是否可复核、Node 故障率和错误恢复情况。

R0 不以 DAU、外部 AI 检出率、自动异常率、学生能力分数或“AI 替代率”作为成功指标。具体可接受阈值应在真实试用前由教师/导师共同确认；未预先确认时，只能报告事实和局限，不能在试用后倒推“成功”。

研究使用另需独立目的、授权、最小化、去标识化、版本冻结和保留/退出规则。R0 产物只能提供受控任务条件，不自动证明职业教育结论。
